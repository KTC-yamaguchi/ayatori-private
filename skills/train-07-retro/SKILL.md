# Step 07: 振り返り（セッションC）

**磨く力**: 6能力の自己認識（レーダーで現在地を捉え、次に伸ばす方向を自分で決める）

**舞台**: セッションC。進行は 📚AIファシリテーター、**種明かしと、ゲートで返した判断の振り返りのときだけ
🙎‍♂️ 担当者（オーナー）が再登場**。
**採点しない／合否・点数を出さない**。立ち位置は「気づき」と「抜け漏れの見える化」＝形成的フィードバック。

**ネタバレ防止（最重要）**: 📚（main）は**最後まで正解ファイル（`scenarios/*.json`）を開かない**。正解を要する処理
（型B のオーナー判定・全型の reveal）は `ayatori-train-persona` subagent 経由。重い全画面 HTML 列挙は truth を
持たない `ayatori-train-enumerator` subagent へ。main は「正解の要らない処理」（要件フィルタ・台帳の仕分けと
引き算・学習者が返した判断との突合・dialogue-log トレース）だけを担う。

## 前提・入力（この app_name の artifacts のみを読む）

- `session.json` の当該 `app_name`（`_train-…`）の `artifacts/{app_name}/` **のみ**を入力にする（再走は別フォルダ）。
- セッションC の開始判定（緩判定）: `pipeline-state.json` の `step21_approved_at` set（または `screens_human_approved`）
  ＝「ゲート21 承認済み以降」。行き過ぎ（23承認・24/25 スタブ完走）でも C に入れる。
- 入力に使う既存記録（**本体改修ゼロ**）:
  - `feedback-log.md`（Pattern A）＝ゲートで出した指摘＝「指摘できた」分
  - `requirement-deviations.json`＝機械検知した要件外要素＝層1（引き算に使う）。**加えて、要件・デザイン・画面の
    各ゲートで学習者が返した判断（`resolution`）の記録**でもある。判断の正誤評価に使う（Phase 1 step 2b。
    対象の絞りは `phase` で行うため、ゲート番号には依存しない）
  - `dialogue-log.md`＝オーナーとの全やりとり＝型C の掘り残し・オーナー未発言判定
  - `understanding-notes.md`＝ B/P の ✓/△/? と目標整理シート（＋ `## メモ` 節があれば、訓練中のコンサルタント自身の
    気づき・仮説として**任意で**振り返り材料に使う。無くてもよい）
    - **シートの扱い（オート記入だった回・本 skill でシートを読む *すべての* 箇所に適用）**:
      `session.json.transcription_mode == "assisted"` の回は、**B/P シートの値・✓・欄の割り当ては 📚 が付けたもの**
      （学習者の判断ではない）。したがって **(a) シートの値を学習者の判断・功績の証拠に使わない**、
      **(b) オーナーが求めたことの抽出源は `dialogue-log.md`（発話）を主とし、シートは補助に留める**、
      **(c) シートに無い / 空欄であることを、学習者の抜けの証拠に使わない**（📚 が迷って保留した欄・設定として
      省略を許した G1/G2 が空欄になりうる。空欄は「判断材料なし」として扱い、「取りに行けば出たのに聞けなかった」
      という言い方をしない）。**目標整理シート（G1・G2）は設定によらず学習者が書く欄**なので、**書かれていれば**
      学習者の判断の証拠として使ってよい。
      - **判断材料なしのときの提示**: 「良い判断」とも「無自覚の抜け」とも決められない場合は、**事実だけを示して
        次に見る場所を渡す**（原因を学習者に帰属させない。📚 が写し損ねた・設定として省略を許した可能性を
        排除できないため）。
      箇所ごとに書き分けず本規則を一律に適用する（読む場所が増えても穴が空かないようにするため）。
  - `screens/{web,mobile}/*.html`（デフォルト画面のみ・`--{state}` サフィックス＝sub-state は対象外）
  - `requirements/*.md`（`requirements/00-raw-input.md` を含む＝学習者がステップ4で `/ayatori-question` に入力した回答逐語。Phase 1c の AI伝達突合の主対象）
  - `requirements.json`（`requirements/` の外・artifacts 直下。Phase 1c の補助参照）

## Phase 0: 再開・冪等性

`session.json.step7_state`（`started` / `revealed` / `radar_updated` / `completed`）で進行を管理する。
- 開始判定（`step21_approved_at`）は「一度立つと消えない時刻」なので、**再開位置は `step7_state` で判定**する
  （時刻だけだと再開のたびに最初からやり直し＝二重化するため）。
- `completed` なら「この回の振り返りは完了済みです」と表示して終了。
- それ以外は該当段階から続ける（未完了段階だけ実行）。ただし reveal 本文（persona の in-character 出力）は Phase 2 で `step7_state="revealed"` を立てた後、Phase 4 まで成果物に永続化されない（それまでチャット文脈のみ・main は正解ファイルを持たず自力復元できない）。このため **`radar_updated` / `completed` 以外（＝ `started` / `revealed`）からの再開では Phase 1 から再走**し、reveal を取り直してから Phase 3/4 を実行する。
- 冪等化: understanding-notes の「振り返り」節は**追記でなく当該節の全置換**。play-log の完了記録は
  **train-00 が開始時に `completed:false` で append 済みの同一 `app_name` entry を探し、その `completed`/`completed_at` を
  更新する**（新規 append しない＝重複させない。万一 entry が無ければ 1 件だけ append）。
- 開始時に `step7_state = "started"` を `session.json` に記録。`current_step` を **`7`** に更新。
- **案内の順序**: 振り返りは「まず気づき（Phase 1〜4）→ 最後にレーダー更新（Phase 5）」の順。**レーダー更新の
  案内はここ（冒頭）では出さない**（Phase 5 まで先出ししない）。開始時は「今日の振り返りをしましょう」程度に留める。

## Phase 1: 型B 突き合わせ ＋ ゲート判断の突合（3段方式）

1. **列挙（truth なし subagent）** — Agent tool で `ayatori-train-enumerator` を起動（入力: `app_name`）。
   デフォルト画面 HTML から機能・UI要素のリストのみを受け取る（main の文脈を汚さない）。screens が無ければこの段は
   スキップし「画面が未生成のため型B の画面列挙は省略」と記録。
2. **仕分け（main・正解不要）** — 下記 **2b → 2a** の順で行う（順序が逆だと未判断の項目が「見逃し」に化ける）。

   **2b. リストの仕分け（`requirement-deviations.json`）** — 台帳を Read し、`entries[]` を次の決定論フィルタで
   2バケットに分ける。**この仕分けは step 1（画面列挙）のスキップとは独立に必ず実行する** — requirements /
   design phase の項目は画面と無関係に存在するため、screens 不在で 2a 由来が 0 件でも本仕分けは走らせる。

   - **台帳が存在しない場合**（AI が要件外追加をしなかった回＝lazy_init で未生成）は本仕分けをスキップし、
     **2b 由来 0 件**として 2a のみで進む（「無し」でよい・欠損として扱わない。他の入力と同じ不在分岐）。

   | 条件 | バケット |
   |---|---|
   | `phase` ∈ {`requirements`, `design`, `screens`} かつ `deviation_kind` ∈ {`要件外追加`, `根拠薄弱`} かつ `resolution` が set | **判定対象** |
   | 上記のうち `resolution` 未記録 | **引き算** |
   | `deviation_kind` ∈ {`想像デフォルト`, `要件矛盾`, `要件削除`} **または** `phase` ∈ {`delta`, `substate`, `reverse`}（どちらか一方の該当で足りる） | **引き算** |
   | 上記いずれにも該当しない値（**未知の enum を含む**） | **引き算**＝包括 fallback |

   - **`raised_by_step` では絞らない**（`18-design-review` は writer で人間への提示は 21 のため）。絞りは `phase` で行う。
   - **`resolution` 未記録は安全網であり正常経路ではない**: 「全件容認 (N 件)」等の一括操作でも各項目に
     `resolution: 容認` は書き込まれる（一括だった事実は別 field に残るだけ）ため、正常に完走した訓練では
     このバケットは**空になるはず**。空でないのは per-item 導線の導入前に作られた旧 artifact か、ゲート中断の痕跡。
     **「まとめて承認」を判断なし扱いする分岐ではない。**
   - **粒度ガード（載せる方を定義する）**: candidates に載せるのは **オーナーが要望として語りうる単位＝
     AI が足した「機能」または「ユーザーに見える情報の種類」** に限る（足された先が `requirements/*.md` /
     トークン / 画面のいずれかは問わない — 上の仕分け表の 3 phase すべてで同じ基準。オーナーは成果物のどこに
     書かれたかではなく要望の単位で語る人だから）。次は判定対象から外して**引き算**へ回す:
     文言・ラベル・見出しの言い回し／空状態・エラー・ローディングの表示のしかた／並び順・初期値・表示件数・
     日付書式／配色・余白・部品の見た目／数値・式・閾値／技術前提（外部 API・ライブラリ等）。
     オーナーは作りも文言も決める人ではないため渡しても判定が
     空回りし、この層は修正ループごとに追記されて件数も膨らむ。**判断に迷う粒度は引き算側に寄せる**
     （誤りとして提示する側に寄せない＝偽陽性で凹ませない。「間違い」と告げるコストは非対称）。
   - **名寄せ**: 同じ要素の項目が**複数 entry に存在する場合（同一 phase・同一 `raised_by_step` の修正ループ由来の
     重複を含む。`18-design-review` は 17→18→19→20→21 ループの毎周で append するため、これが最も多い）**は、
     **`resolved_at` が最も遅い項目の `resolution` 1 件に名寄せ**して判定する（最終判断が成果物に立つため）。
     同一要素に矛盾する 2 評価を並べない（ループ内で `修正依頼` → `容認` と変わった場合も最遅の `容認` を正とし、
     後述の「名寄せ由来のトーン補正」を適用する）。
   - **判断時刻の比較規則（本 step 以降で `resolved_at` を並び替え・比較に使うときは常にこれに従う）**:
     `resolved_at` は任意 field なので欠落し得る。**無い項目は `detected_at` で代替**し、それも同時刻なら
     **`requirements` → `design` → `screens` の後段**を後（新しい）とみなす。名寄せと、後述「候補の並び順規則」
     の第 2 段が本規則を使う（欠落 entry があっても順序が一意に決まる＝決定論を保つ）。
   - **候補の並び順規則（2b 由来の候補を並べ替え・選抜するときは常にこれに従う。candidates の絞り込みと
     Phase 3 の提示順の両方が本規則を参照する — 同じ規則を 2 箇所に書いて片方だけ育つのを防ぐ）**:
     1. `severity` 降順（`high` → `medium` → `low`）。**`severity` 欠落は `low` と同じ位置**に置く
        （schema の機械判定は `low` が受け皿で必ず値が入る建て付けだが、任意 field なので欠落自体は
        起こり得る。その場合の位置を未定義にしない）。
     2. `resolved_at` 昇順（先に判断を返したもの。欠落時は上記**「判断時刻の比較規則」**に従う）。
     3. なお同値なら **`entries[]` の 1-based index 昇順**（= view の `#N`。台帳は append-only のため
        run をまたいでも安定し、学習者が view で見た番号順と提示順が一致する）。
   - **判断の答え方（一括 / 1 件ずつ）は良し悪しの判定に使わない**: `resolution_mode` の `bulk` は
     件数を明記した意識的な明示選択の記録にすぎず、注意の払い方やレビューの質を示すものではない
     （`docs/principle4-disambiguation.md` §5.5 の consumer 別表が SoT）。使うのは**声のかけ方の文脈**だけ
     （一括だったなら「まとめて確認したときは 1 件ずつ見ると気づきやすいです」、1 件ずつなら
     「1 件ずつ見たうえでの判断でしたね」と一言添える程度）。**`resolution_mode` の欠落を `bulk` と同義に扱わない**。

   **2a. 要件フィルタ（列挙要素）** — step 1 の列挙要素を `requirements/*.md` と照合し「要件に含まれない＝
   AI が足した候補」を抽出する。ただし **2b で引き算バケットに入った項目と意味一致するものは
   candidates から除外**する（照明を当てない・「ここは AYATORI も気づけた」と一言のみ）。
   - **2a と 2b 判定対象の両方に一致する（または一致が確信できない）候補は 2b 由来として 1 件に寄せる** —
     判断が記録されている方が原因段階として正しいため（同じ要素を「見逃し」と「判断を誤った」に二重で出さない）。
     ここは後述「不確信は見逃しに寄せる」規則の**例外**（寄せ先が空振りではなく別区分だから）。

3. **オーナー判定（persona subagent）** — **2a 由来 ＋ 2b 判定対象** をマージした `candidates[]` を
   `ayatori-train-persona`（`mode: "judge_features"` / `scenario_id`（session.json から取得）/ `candidates[]` /
   `dialogue_log`＝`dialogue-log.md` の全文）に渡し、一件ずつ `NG / どちらでもない / 歓迎` ＋理由を人格判定で受け取る
   （dialogue_log は訓練中に語った・断った経緯と矛盾しない判定のために必須）。
   - **2b 判定対象は `element` / `description` から「オーナーが分かる機能・要望の言葉」に言い換えた要素名**を
     candidates に載せる（台帳の `element` は `.md` 識別子や実装語になり得る。そのまま渡すとオーナー役が
     何の話か分からず全件 `どちらでもない` に落ちて判定が空回りする）。main は
     **言い換え後の要素名 → `{element, resolution, severity, artifact, phase}`** の対応表を保持し、
     以降の突合とシート記載はこの表を経由する（candidates と対応表のキーを一致させる）。
     言い換えが作れない（何の機能か読み取れない）項目は判定に載せず引き算へ回す。
     **persona が返した要素名が対応表のキーと一致しない項目は、その判定を採用せず引き算へ回す**
     （persona 側は要素名を逐語で返す規約だが、崩れたときに黙って全件が突合不能へ落ちるのを防ぐ）。
   - 重複は意味一致で 1 件に寄せる。**出所（2a 由来 / 2b 由来）は persona に渡さない**
     （「学習者が既に容認したもの」と知らせると判定にバイアスが入る）。
   - **candidates の上限**: 2a 由来を優先し、**2b 由来は step 2b の「候補の並び順規則」の先頭から
     最大10件**に絞って渡す。提示は最大2件なので全件を裁く必要がなく、オーナー役は
     候補数が増えるほど人格の一貫性と `dialogue_log` との整合が落ちる。絞って落ちた分は引き算扱いとし、
     件数も提示しない（「ほかに N 件」に混ぜない）。
   - **candidates が 2b 由来のみ（画面未生成等で 2a が 0 件）でも step 3 は必ず実行する。**
   - candidates が 0 件のときのみ step 3 を省略する。

### 「指摘できた／見逃した」の確定（semantic 照合）

`feedback-log.md`（自然文）／`requirement-deviations.json`（.md 識別子）／列挙結果（HTML 要素）は**共通キーを持たない**
ため、機械的な集合演算はできない。**照合は意味で行い（この自然文の指摘は、この要素/台帳項目と同じことを指すか）、
一致が確信できないものは安全側＝「見逃し」に寄せる**（成功を水増しするより見逃しに寄せて次の一手を返す方が形成的）。

3パターンに分類（採点しない文型）。**対象は 2a 由来の候補のみ** — 2b（リスト）由来の判定対象は次節
「並べられていたのに判断を誤った」で扱い、本 3 パターンには入れない（別枠・排他）:
- **出た＆指摘できた** → 「ゲートで止められましたね。実案件でもここが人間ゲートの役割です」（成功体験の言語化）
- **出た＆見逃した** → 「この画面にこれが出ていました。オーナーは実は NG でした（理由）。こう見れば気づけます」＋ reveal
- **出なかった** → `judge_features` に候補が無くても、reveal で `ng_features` を種明かし「実案件ではこういうものを足して
  くることがあります。レビューではここを見ます」（罠の存在自体を教材化）

### 「並べられていたのに判断を誤った」の確定（2b 由来・トレーニング固有）

**この区分は上の 3 パターンとは別枠・排他**（2b 由来の項目を「出た＆指摘できた／見逃した／出なかった」には入れない）。
目の前のリストに並んでいたのだから「見逃した」ではなく「**並べられていたのに判断を誤った**」である。
リストに並んだものが正しい追加とは限らず、**その判断が正しかったかはオーナー役を持つ本モードでしか判定できない**
（素の本体パイプラインには判定材料が無い）。これがトレーニングモードでのみ成立する観点。

**突合マトリクス**（オーナー判定 × 学習者がゲートで返した判断）:

| オーナー | 学習者 | 区分 | 扱い |
|---|---|---|---|
| `NG` | `要件に昇格` | **誤り** | 提示。＋「これは要件の側に入ったので、この先も要件として扱われます」を事実として添える（重さの序列ではなく次の一手のための情報） |
| `NG` | `容認` | **誤り** | 提示 |
| `歓迎` | `修正依頼` | **誤り（責めない文型）** | 提示。「要件には無かったけれど、ここまでのお話をもとにすると、これは必要なものでしたね」と**中身を名指し**し、**次の一手は必ず「照合（基準1）で引っかかったものは、消す前に一度オーナーに聞き戻せた」に接続する**（訓練中は聞き戻しの相談窓口、実案件ではオーナーへの確認）。この 1 種だけは「見れば気づける」ではなく**「聞けば分かる」型**の誤りなので、他 2 種と一手の種類が違う |
| `NG` | `修正依頼` | できたこと | Phase 3-① で一言（機械も気づけて、判断も合っていた） |
| `歓迎` | `要件に昇格` | できたこと（最善） | Phase 3-① で一言 |
| `歓迎` | `容認` | — | 引き算（照明を当てない） |
| `どちらでもない` | 任意 | — | 引き算 |
| 3 値以外・判定欠落 | 任意 | — | 引き算（fallback） |

- **引き算ルール**: リストに載っていて **かつ 判断が誤りでない** ものだけ引き算する。
- **誤り3セルは同格**に扱う。いずれも「オーナーの意向を読み違えた」という同じ目利きの誤りで、学習の価値も同じ。
  型ごとの重み付けの序列を作らない（下流被害の大きさで誤りをランク付けするのは判断の質の話ではなく、
  採点しない原則とも衝突する）。
- **提示は最大2件**（③ の型C/型D と合わせると別格枠が膨らみ「情報過多を防ぐ」意図を割るため）。順序は
  step 2b の**「候補の並び順規則」**に従う（3 段の tie-break で提示内容を決定論にする）。
  あふれは「ほかに N 件」と件数のみ。
- **Phase 2 reveal との統合（二重に語らない）**: `ng_features` 由来の要素は reveal（型B/型D）にほぼ確実に再登場する。
  同一要素は **reveal を正**とし、本区分側では「そのときゲートではこう判断していましたね」の一言だけ添えて 1 件に統合する。
- **Phase 1b / 1c との統合**: 同一要素が実行時乖離としても出た場合は**本区分に帰属**させて 1 件にする
  （リストに並んで判断済み＝原因段階はゲートの判断）。Phase 3 の枠を同一要素で 2 枠消費しない。
- **成功側の二重カウント防止**: `修正依頼` は `feedback-log.md`（Pattern A）にも残り「出た＆指摘できた」の材料になる。
  同一項目が両方に一致する場合は 1 件に統合し ① で一度だけ言う。なお `resolution` = `修正依頼` / `要件に昇格` は
  **機械的証跡**なので、semantic 照合の「不確信は見逃し寄せ」規則の**例外として、「指摘した事実」（Pattern A の
  自然文と本項目が同一のものを指すこと）は照合の確信を待たず確定してよい**。ただし**例外の射程はここまで**で、
  **成功／誤りの区分はあくまで上記突合マトリクスの結果に従う**（`歓迎`×`修正依頼` / `NG`×`要件に昇格` は
  マトリクス上「誤り」であり、機械的証跡があっても ① には載せない）。
- **名寄せ由来のトーン補正**: 名寄せで「design では止めたのに screens で容認」となった要素は、
  「一度は止められていましたが、最後は通してしまいましたね」の形成的な一言を添えてよい（誤り一色にしない）。
- **学習者向け文面の呼び方**: 「ゲートで並んでいたリスト」「あのとき返した判断」と呼ぶ。内部語
  （台帳 / `resolution` / `resolution_mode` / `deviation_kind` / 型B 等）と **リスト項目名（`element`）の逐語を
  そのまま出さない**（画面の言葉に言い換える）。
- **区分名そのものも内部語として扱い、学習者向けの発話・見出しに出さない**（「並べられていたのに判断を誤った」は
  設計用語で、「並べられていたのに」は責めの含意を持つ）。学習者向けの見出しは
  **「ゲートで並んでいたリストの判断を振り返る」** に固定し、各件は **「このとき、こう判断していましたね」**から
  始める（事実の確認から入り、責めの含意を作らない）。
- **ゼロなら何も出さない**（粗探しして軽微な差を誤りに仕立てない。チェックの実施自体は必須だが結果ゼロは「無し」でよい）。

## Phase 1b: 要望↔成果物クロスチェック（main・正解不要・シナリオ外の逸脱検知）

Phase 1 の突き合わせは**シナリオの正解（hidden_settings）起点**のため、**シナリオに書かれていない実行時の乖離**
（例: オーナーは「スマホ中心」と言った ↔ 成果物は PC/web 画面のみ）は検知できない。ここは正解ファイル不要で
main が検査できる領域なので、**独立の必須チェック**として行う:

1. **「オーナーが確定的に求めたこと・その場で確定させたこと」を抽出** — `dialogue-log.md`（オーナーの発話）と
   `understanding-notes.md` の ✓（事実）項目から、**成果物の形に直結する確定要望**を列挙する。
   **オーナーがヒアリング中にその場で確定させた事実（数字・条件・優先度・手応え・相談の上での取捨）も同じ対象**
   に含める —— それがシナリオの正解由来か、その場の即興かは **main には判別できないし、判別する必要もない**
   （オーナーの発話は全て「その回の事実」。即興かどうかの識別は Phase 2 の persona reveal が行う）。
   特に必ず見る観点:
   - **プラットフォーム / 利用シーン**（P4。スマホ中心か・PC か・両方か）
   - **コア機能・見せ方**（P3。「絶対要る」とされたもの）
   - **成果物イメージ・範囲**（P6）と **G1/G2**（ゴール・やらないこと）
2. **成果物と突き合わせる** — 各確定要望が (a) `requirements/*.md` に反映されているか、(b) 実体
   （`screens/web/*.html` / `screens/mobile/*.html` の存在・画面/機能の有無）に現れているかを確認する。
   例: P4 が「スマホ中心」なのに `screens/mobile/` が無い／web のみ → **乖離**。
   - **main は HTML 本文を読み直さない**（重い読み込みは enumerator 隔離の原則を守る）: 画面/機能の有無は
     **Phase 1 で受け取った enumerator の列挙結果を再利用**して照合し、main が直接見るのは
     ディレクトリ一覧（`screens/web|mobile` の存在・ファイル名）までに限定する。
3. **乖離の扱い（形成的・断罪しない）** — 乖離を見つけたら、まず `feedback-log.md`・G2・ゲートでのやりとりに
   **意図的なスコープ判断の記録があるか**を確認する:
   - **記録あり（意図的判断）** → 「オーナーは◯◯と言っていましたが、△△という判断で今回は□□にしましたね。
     その判断をオーナーに伝えて合意を取れたか」を問いかける（判断の言語化訓練）。
   - **記録なし** → 断定する前に、**まず境界マーカー判定を行う**: その要望の初出が `dialogue-log.md` の境界マーカー
     （`--- Step 4 引き継ぎ` で始まる行。正書は
     `--- Step 4 引き継ぎブリーフィング済み（以降のオーナー発話は引き継ぎ後の聞き戻し） ---`。中断→再実行等で
     複数あれば**最初の1本**を境界とする）より**前**か**後**かを見る。
     - **初出がマーカーより前（または境界マーカーが無い旧ログ＝後方互換）** → 従来どおり
       **重要度 high の見逃し**として Phase 3-④ に必ず含める（「オーナーは◯◯と言っていたのに、成果物は□□でした。
       ゲートの基準2（抜け）で見る場所です」＋気づき方をセット）。
     - **初出がマーカーより後**（＝引き継ぎブリーフィング完了後の聞き戻しで引き出した情報） →
       見逃しではなく **『インプット漏れ』区分**として扱う。**ヒアリングは成功しており、
       AYATORI への追加インプットが残っただけ**なので、ヒアリング能力の問題にしない。ただし聞き戻しの案内
       （phase「未反映の注意喚起」）は「反映しない判断も可」と伝えているため、**入れ忘れと断定せず本人に問う形**で出す:
       > 「聞き戻しで◯◯を引き出せていました（**ヒアリングとしては成功**）。ただ成果物には反映されていません。
       >  これは**反映しないと判断した**のでしょうか？ それとも**入れ忘れ**でしょうか？（**AYATORI に入れたのに
       >  反映されていない**なら、それも教えてください）。入れ忘れなら、次回は聞き戻しで新しく決まったらその場で
       >  反映を（要件承認前なら該当ステップの会話で補足、承認後なら `/ayatori-req-delta`、画面まで完成した
       >  後なら `/ayatori-delta`）。」
       - マーカー以降の `dialogue-log.md` に「今回は反映しない」等の**意図的判断のやりとりが残っている**場合は、
         問わずに上の「記録あり（意図的判断）」と同じ扱いにする（判断の言語化を評価）。
       - **「入れたのに落ちた」と答えた場合**は本区分ではなく **「AYATORI 側の落ち」＝ Phase 1b 帰属**に付け替える
         （Phase 1c-5 の「入力にはあるのに成果物に無い」と同じ扱い＝ゲートで拾えたかの目利き / 補完の話。
         学習者の伝達力・インプット漏れにはしない）。
       - 引き出せたこと自体は Phase 3-① の「できたこと」側でも言及する（評価を下げない）。
4. この結果は Phase 3 の提示（④ 残りの気づき、乖離が最重要なら ② 今日の1点）に合流させ、Phase 4 の
   振り返りシートにも「シナリオ外（実行時乖離）」として1行残す（型欄は「抜け（実行時）」、
   『インプット漏れ』区分なら「インプット漏れ（実行時）」と表記）。
5. **乖離が無ければ何も提示しない**（粗探しして軽微な差を乖離に仕立てない。チェックの実施自体は必須だが、
   結果ゼロはそのまま「無し」でよい＝採点しない・凹ませない原則）。
6. **P2 用の材料を組む（Phase 2 reveal へ渡す）** — 上記に加え、正解不要の範囲で次の2つを用意する:
   - `dropped_candidates`: `dialogue-log.md` で**オーナーが述べた要望・前提（✓確定に限らず即興・想像含む）**を列挙し、
     成果物（`requirements/*.md` ＋ Phase 1 の enumerator 列挙）と突き合わせて**「述べられたのに成果物に落ちている候補」**を抽出（要素名の配列）。
     - **境界マーカーより後が初出の候補は `dropped_candidates` に含めない**（Phase 1b-3 の
       『インプット漏れ』区分として 📚 が扱う。persona に渡すと reveal が「取りこぼし＝失敗」として in-character
       指摘し、①「ヒアリング成功」の提示と矛盾＋二重報告になるため）。
   - `deliverable_summary`: 成果物の**主要な確定事項の匿名サマリ**（例:「ターゲットを◯◯に絞った」「ログイン必須にした」
     「△△機能を入れた／◯◯を入れなかった」）。
   これらは main では「シナリオに反しないか／拾う価値があるか」を判定しない（正解を持たないため）。**判定は Phase 2 の
   persona reveal に委ねる**（persona が ground_truth で 取りこぼし＝拾う価値ありのみ／ドリフト＝逆行 を選別して返す）。

## Phase 1c: AI伝達クロスチェック（main・正解不要・「伝えた」段階の抜け/歪み検知）

「AI伝達」＝ステップ4で**掴んだ理解を `/ayatori-question` にどう入力（翻訳）したか**の力。この材料は Phase 1/1b
（成果物側の突合）では取れないため、**独立の必須チェック**として行う。突合するのは「オーナーが実際に話したこと」↔
「学習者が AI に入力したこと」で、いずれも正解ファイル（ground_truth）ではないので main が直接読んでよい。

1. **入力成果物の有無を確認** — `artifacts/{app_name}/requirements/00-raw-input.md`（主・学習者の回答逐語）を Read。
   `requirements.json`（`artifacts/{app_name}/requirements.json`・**`requirements/` の外**）は補助参照。
   **`00-raw-input.md` が無い**（ステップ4未実施等）→ AI伝達は**「今回は判断材料なし」**として本 Phase を終了する
   （据え置き・でっち上げない）。
2. **オーナーが伝えた要点を再利用** — Phase 1b-1 で `dialogue-log.md` から抽出した「オーナーが確定的に求めたこと」＋
   Phase 1b-6 の `dropped_candidates`（オーナーが述べた要望・前提）を**再利用**する（dialogue-log を読み直さない）。
   真値＝オーナー発話。
3. **入力へ届いたかを突合** — 各要点が `00-raw-input.md` に反映されているかを確認し、**抜け**（オーナーが言ったのに
   入力に無い）／**歪み**（意味が変わって入力された）を拾う。
   - **突合の正は `00-raw-input.md`（回答逐語）**。`requirements.json` は補助にとどめる — json は AI が構造化した
     派生物なので、「raw-input には正しくあるのに json で歪んだ」は AYATORI 側の構造化の癖であり**学習者の伝達力の
     指摘対象にしない**。
4. **意図的スコープ判断を先に除外**（Phase 1b-3 と同じガード） — 抜けに見えるものは、まず G2「やらないこと」・
   `understanding-notes.md`・`feedback-log.md` に**意図的に伝えなかった記録**があるかを確認する。
   - **記録あり**（例: 型Dを後続送りにした・G2 に置いた）→ 抜けではなく**良い判断**として「できたこと」側で言語化。
   - **記録なし** → 無自覚の伝達漏れとして扱う（型D スコープアウトの成功を「漏れ」と誤指摘しない）。
5. **Phase 1b との重複統合（二重報告禁止）** — 同一要点が Phase 1b（成果物側）でも検出された場合は **1件に統合し、
   原因段階に帰属**させる:
   - 「入力（`00-raw-input.md`）に無い」→ **AI伝達の抜け（本 Phase 帰属）**。下流の成果物欠落は当然の帰結なので
     Phase 1b 側では重ねて出さない。
     - **例外（引き継ぎ後に出た情報）**: その要点の初出が `dialogue-log.md` の境界マーカーより**後**（＝引き継ぎ
       ブリーフィング完了後の聞き戻しで引き出した情報）なら、**AI伝達の抜けにしない**。引き継ぎ時点では
       まだ存在しなかった情報なので、入力に無いのは当然。Phase 1b-3 の **『インプット漏れ』区分に帰属**させ
       （1件に統合・二重報告しない）、AI伝達の根拠には数えない。マーカーが無いログでは従来どおり。
   - 「入力にはあるのに成果物に無い」→ **AYATORI 側の落ち（Phase 1b 帰属＝ゲートで拾えたかの目利き/補完の話）**。
     学習者の伝達力ではない。
   - Phase 3 の8件枠を同一要点で2枠消費しない（この因果切り分けが本 Phase を足す価値）。
6. **形成的に扱う** — 見つかった抜け・歪みは「オーナーは◯◯と言っていたが、AI への入力（要件）では□□に
   なっていた。**こう書けば漏れなく伝わった**」の形（断罪しない・次の一手とセット）。
7. **無ければ「無し」** — 粗探ししない。結果ゼロはそのまま無し（Phase 1b-5 と同じ・採点しない/凹ませない原則）。
8. **合流先** — 結果は Phase 3-④（残りの気づき／影響大なら②）と Phase 4 振り返りシート（型欄「AI伝達（実行時）」・
   関係能力=AI伝達）へ。Phase 5 の `ai_communication` 根拠1行の紐付け元にする。

## Phase 2: 全型の reveal（persona subagent）

Agent tool で `ayatori-train-persona`（`mode: "reveal"` / `scenario_id` / `dialogue_log` 全文
**＋ Phase 1b-6 で組んだ `deliverable_summary` / `dropped_candidates`**）を起動し、
**さらに次の引用ブロックを起動プロンプトに必ず添える**（長い reveal 生成で落ちやすいため呼び出し側から毎回要求する）:
> 「①`hidden_settings` は**全件に触れること**。ただし**reveal 全体で 1,200 字前後**に収め、**1件あたりの厚みで
> 調整**する（型C=4〜5文／作られている NG 機能（型B）=2〜3文／お願いしたのに落ちているもの=1〜2文／
> **その他の軽いものは各1行**）。**軽いものを省かず、1行で触れる**こと。1行のときも話し言葉のまま
> （箇条書き・体言止めの羅列にしない。複数を1文にまとめてよい）。
> **型D は `dialogue_log` を見て、その願望を自分（オーナー）が口にした発言があるものは繰り返さない**
> （それは 📚 が①できたことで扱う。事実に反する『言い出せていませんでした』を付けるのも禁止）。
> 口にしていなかった型D は「実は〜も頭にありまして、今日は言い出せていませんでした」と一言添えて明かす。
> ②`dropped_candidates`（お願いしたのに落ちているもの）は、`ground_truth` 由来かその場の即興かで扱いを変えず、
> 同じ形で事実として指摘すること。**「これはその場でお答えした話です」「資料には無い」等、由来を明示する言い方は
> 書かない**。**成果物の形に効かない即興（目標値の目安・手応えの数字など）には触れないこと**（直す先が無く
> 行動につながらないため）。
> ③聞き方のコツ・次の一手・次回コツ・教訓は書かないこと（ファシリテーターが担当）。1項目2〜3文まで、型C のみ
> 4〜5文まで。**前置き・予告・目次的な枕を書かず1文目から核心に入る**（✗「順にお話しします」）。会話のなぞり返し・
> 成果物の説明の反復もしない。詫び・自責は全体で1回だけ。
> ④成果物を褒めないこと。成果物に触れるのは『入っていない』『入ってしまった』の事実指摘だけ。
> できたことの言語化はファシリテーターが担当する。」

**上記引用ブロックの数値・厚み配分の正本は `.claude/agents/ayatori-train-persona.md` §reveal**
（1,200 字前後 / 型C 4〜5文 / 軽いものは各1行 等）—— ここは呼び出し時の再掲であり、
**変更するときは両方を同時に更新する**。

`hidden_settings[]` を `surfaced_at` 順に全開示した in-character の reveal を受け取る。**抜けの正本はこの全開示**
（understanding-notes の ?空欄は「取りに行けば出た」の補助フレーミング）。
**分量は「落とす」ではなく「厚みで調整」**: 全件に触れたうえで **reveal 全体 1,200 字前後**に
収まるよう、軽い裏設定は各1行に圧縮される（型C は4〜5文と厚い）。渡しすぎると訓練中のコンサルタントが見切れない
ためで、**省略ではない**。ただし**型D のうち学習者が掘り出して対処まで済んだものは重複回避で出てこない**
（それは 📚 が「① できたこと」で扱う）。受け取った reveal を振り返りシートの
reveal 列（「こう届いた」「NG理由」）へ**転記**する（main は正解ファイルを開かない）。完了したら
`step7_state = "revealed"`。

**P2（取りこぼし＆ドリフト）の受け取り**: persona は上記入力があるとき、型A〜D の全開示に加えて
(a)**取りこぼし**（オーナーが述べたのに成果物に落ちた、シナリオに反しない重要なもの）と
(b)**ドリフト**（成果物がシナリオの狙い／must と逆行している点）を in-character で返す。
これらを **Phase 3 の提示** に合流させる（(a) は ④残りの気づき、影響大なら ②今日の1点／取り込めていたら「できたこと」で言語化。
(b) は逆行の重さに応じて ②または④）。**採点しない・形成的**（「次はこう聞けば／こう見れば」をセット）。
即興で語られた（ground_truth に無い）要望でも、シナリオに反しなければ拾ってよい＝「毎回話が違っても最後に拾える」を担保する。

**その場で確定させたことも同じ重さで扱う（由来を区別しない）**: オーナーは `ground_truth` に無いことも
その場で確定させて語る（感覚・手応え・優先順位・相談の上での取捨）。それらはその回においては要件と同じ重さの正解なので、
**`dropped_candidates` の指摘は「正解データ由来か即興か」で扱いを変えない**。persona も由来を明示せず
（「これはその場でお答えした話です」等は書かない）、同じ形で「お願いしたはずなのに入っていないようです」と返す。
**main も由来を判定しない**（正解を持たないため判別不能。そして判別する必要もない）。

> **relay 前の機械的フィルタ（📚）**: 逐語で見せる原則は不変だが、**次のパターンが混じっていたら
> その文だけ落として relay する**（正解を知らなくても文字面で判定できるものに限る・要約や言い換えは従来どおり禁止）:
> ①ファイルパス／ファイル名（`skills/...` `.json` 等）②「資料には無い」「正解データ」等 ground_truth の存在への言及
> ③型名（型A〜D）・ティア名（organized 等）④**地の文の判断理由の定型**——話し言葉でない解説文の頭
> （「この問いは〜」「〜という判定のため」「〜と判断しました」「理由:」等）で始まる文。
> **④のみ迷ったら落とさず relay する**（①〜③は文字面で確実に判定できるが、④は判定を誤ると
> オーナーの発話を 📚 の裁量で消すことになり、逐語 relay 原則の穴になるため safe 側へ倒す）。
> 実走で①②の混入を観測しているため、最後の砦として 📚 側に置く（落とした旨を学習者に説明する必要はない）。

> **種明かしはオーナーの声で（📚 が代読しない・必須）**: subagent から受け取った in-character の reveal テキストは、
> Phase 3 の提示の中で **`🙎‍♂️ 担当者（オーナー）：「実は…だったんです」` の話者ラベル付き・逐語**で提示する
> （ステップ7 の 🙎‍♂️ 再登場の主な見せ場。もう一つは Phase 3-③ の「判断を誤った」のオーナー理由）。
> 📚 が要約・言い換えて自分の声で伝えるのは**禁止**
> （reveal の内容整理・教訓化は、オーナーの逐語提示の**後に**📚 が行う）。

## Phase 3: 提示（5構成・情報過多を防ぐ）

**採点しない**。提示は上から順に（**この段階ではレーダー更新の案内はしない**＝レーダーは Phase 5）:

1. **① できたこと先行** — 「指摘できた／掘れた」を先に返す（成功体験を上に）。**成果物の「できたこと」を
   言語化するのは 📚 の担当**: オーナーは成果物を褒めないので、`deliverable_summary` と
   Phase 1 の enumerator 列挙を突き合わせ、**入っていた／自分で止められた分を 📚 が自分の言葉で褒める**。
   （理由: 正解を持つ persona 側に褒めさせると、実走で summary と逆のことを褒める事故が起きた。
   `deliverable_summary` を持つ 📚 が突き合わせれば事実は壊れない。オーナー側が褒めない規約は
   `.claude/agents/ayatori-train-persona.md` §reveal「成果物を褒めない」、**📚 が褒める手順は本節が正本**）
   - **Phase 1b-3 で『インプット漏れ』区分になった要望は、ここで「引き出せたこと」を評価する**
     （「引き継ぎの後にちゃんと聞き戻して◯◯を引き出せていました」）。**反映漏れの指摘は ④ 側**に置き、
     ①では成功として扱う（ヒアリング成功と反映忘れを混ぜない）。
   - 「並べられていたのに判断を誤った」の**正解2セル**（`NG×修正依頼` / `歓迎×要件に昇格`）は、ここで
     **まとめて一言**（例「ゲートで並んでいたもののうち、◯件はオーナーの意向どおりに裁けていました」）。
     件数は項目行数ではなく**名寄せ後の要素数**で数える（同じ機能が修正ループごとに複数行載るため、
     行数で数えると水増しになる）。ただし **重要度が上位の1件だけは名指しで**「◯◯はゲートで止められましたね。
     実案件でもここが人間ゲートの役割です」と返してよい（件数の一言だけで済ませると誤り側だけが手厚くなり、
     「できたこと先行＝成功体験を上に」の実効が落ちる）。深追いはしない。
2. **② 今日の1点（別格）** — この回で最も大事な気づき1つを別格で立て、深く返す（残りは畳んで下に）。
   - 「並べられていたのに判断を誤った」の誤り3セルは**いずれも候補になれる**（型で限定しない）。
     その回で最も大事なものを選ぶ既存の考え方に委ねる。
3. **③ 種明かし（🙎‍♂️ オーナー再登場・逐語）＋ 別格回収（型C・型D・判断の誤り／いずれも8件枠の外）**:
   - **まず 🙎‍♂️ オーナーの reveal を逐語提示**（Phase 2 の注記どおり話者ラベル付き・「実は…だったんです」を
     📚 が要約せずそのまま見せる）。この提示を**スキップして 📚 のまとめだけで済ませるのは禁止**。
   - **オーナーが語るのは「核心」だけ（分量規約）**: reveal は「実はこうだった＋なぜそうか」
     しか返ってこない（1項目2〜3文・型C のみ4〜5文）。**「どの一問が足りなかったか」「次はこう聞けば」
     「次回コツ」「教訓」は 📚 が逐語提示の直後に自分の言葉で短く付ける**（オーナーがそこまで語ると長すぎて
     肝心の「実はこうだった」が埋もれるため。オーナー側が語らない範囲は
     `.claude/agents/ayatori-train-persona.md` §reveal
     「オーナーが語るのは核心だけ」、**📚 が何を足すかは本節が正本**）。
     これは「📚 が reveal を要約・代読する」ことではない（それは従来どおり禁止）—— **逐語はそのまま見せ、
     指南だけを 📚 が足す**。
   - **型C（掘れなかったビジネス目的・最重要）**: オーナーの逐語（核心＋事情）を見せた直後に、📚 が
     「足りなかった一問の名指し」＋「ここは AYATORI には分からない・あなたにしか取れない情報」＋次の一問を
     短く添える（3点構成のうち 2・3 が 📚 の担当）。
   - **型D（過剰要望）**: 「今回の予算・期間ではスコープ外＝後続開発」と必ず回収（オーナーは2文程度で言う）。
     **次回コツ「『ゆくゆくは』『自動で』が出たら予算・期間の物差しを当てる」は 📚 が添える**。G2 に入れられていたら成功として言語化。**その願望が会話に一度も
     出ていなかった場合**は、subagent reveal がオーナーの「言いそびれ」を認める一言を添えてくるので、それを逐語で
     見せる（見抜けなかった扱いにしない・不公平感を残さない）。📚 が「見逃しましたね」と補ってはいけない。
   - **ゲートで並んでいたリストの判断を振り返る（最大2件・型C/型D と並ぶ別格枠）**: 型C/型D と同じく
     **④ の8件枠には混ぜない**（混ぜると既存の型A/A'/B を押し出す）。この節の最後（型C・型D の回収の後）に置く。
     各件に次の一手を必ずセットする（`歓迎×修正依頼` は「聞き戻せた」型・他 2 種は「こう見れば気づける」型）。
     - オーナーの理由は **`judge_features` が返した1文を逐語のまま**
       `🙎‍♂️ 担当者（オーナー）：「{理由}」` の話者ラベル付き鉤括弧に入れて示す。**句点の付与などの体裁の
       最小整形のみ**で、**内容の加筆・言い換え・膨らませは禁止**（📚 がオーナーの台詞を作らない。正解を持たない
       main が 🙎‍♂️ 名義の発話を発明すると、学習者はそれをオーナーの真意として受け取るため回復不能）。
       1 文として物足りなくても補わずそのまま出す。
     - relay 経路が1本増えるので phase「**オーナー役の応答を relay する前に漏えいチェックする**」
       （実名 / 正解ファイルのキー名 / 型名の混入確認）を必ず通す。
     - **② 今日の1点に昇格した1件はこの枠に再掲しない**（最大件数は残りから数える）。② で深く扱った旨だけ
       冒頭に一言添える（同じ話を 1 回の提示で 2 度させない）。
     - **初回フォールバック（後述）が有効なときは 1 件に絞る**（初回の学習者に誤りを並べて凹ませない）。
4. **④ 残りの気づき（型A/A'/B・最大8件）** — 優先順: (i) 重要度 high の見逃し（落とすとオーナー意図違反／リリース不可級）を
   最優先で含める（クリア済なら「できたこと」側に置き high 枠を粗探しで埋めない）→ (ii) 残りを重要度順に合計8件まで →
   (iii) あふれは列挙せず「他に軽微な気づきが N件あります」と件数のみ。
   - **『インプット漏れ』（Phase 1b-3）は「見逃し」と混ぜず別ラベルで出す** —
     「**インプット漏れ**（聞き出せていたが AYATORI に未反映）」と明記する。**重要度は影響度で付ける**
     （オーナーの NG が未反映などリリース不可級なら high 可。「ヒアリング成功」はラベル＝帰属の話であって
     影響度を下げる理由にしない）。次の一手は「聞き戻しで新しく決まったら、その場で AYATORI に反映
     （要件承認前なら該当ステップの会話で補足、承認後なら `/ayatori-req-delta`、画面まで完成した後なら
     `/ayatori-delta`）」で固定。
5. **⑤ 締めの次アクション** — 「次はこのシナリオ／この能力を狙うといい」の具体的な一言で閉じる（レーダーのへこみ＋
   play-log 前回比を手がかりに）。

**達成度は3値**（型共通）: `できた` / `部分的にできた（あと一段）` / `できなかった（見逃し・判断の誤り・そもそも出なかった）`。
中間を許し部分的成功を「見逃し」に丸めない。トーンは形成的（見逃しも必ず「こう見れば気づけた」の次の一手とセット）。

**Phase 3 の提示は 200 字上限の対象外（意図的な例外・短縮しないこと）** — phase「📚 の 1 発話は 200 字以内」の
除外項に該当する（種明かし後に 📚 が担当する「どの一問が足りなかったか／次はこう聞けば／教訓／できたことの言語化」は
内容そのものが学習の核）。加えて ③ に逐語 relay を含むため**1 メッセージに収める必要がある**（下記の表示保証）ので、
①〜⑤ を分割してはならない。**ただしトーン規約は効く**: 冗長な言い換え・過剰な励まし・飾り言葉・会話のなぞり返しは足さず、
④ の8件枠・「あふれは件数のみ」等の既存の分量ガードで情報過多を抑える。

**Phase 3 の提示はターン最終出力にする（後続 tool call を作らない）** — ③ に 🙎‍♂️ の逐語 relay を含むため
（reveal と「判断を誤った」のオーナー理由の両方）、phase「🙎‍♂️ relay を含むメッセージはターン最終出力にする」に従い、
①〜⑤（③ の別格枠を含む）の提示メッセージを出したら**そのターンはそこで止める**。Phase 4（振り返りシートの全置換）・Phase 5（レーダー更新）の tool 作業は、訓練中のコンサルタントの
反応・入力を受けた**次のターン以降**で着手する（同一ターンに詰め込むと種明かしが表示から流れ落ちる）。

**初回フォールバック（できたこと0件時）** — play-log で「このシナリオ初回」（＝現在の `app_name` を除いた同 `scenario_id` エントリが0件、または `completed:true` が0件。train-00 が開始時に自セッションの `completed:false` を先行 append 済みのため、自分自身のエントリは初回判定から除外する）と判定したとき有効化:
- できたこと0件なら「初回は見えなくて当然です。今日いちばんの収穫は、**こういう罠が在ると知れたこと**そのものです」
- 8件出さず、② 今日の1点 ＋ 型C を中心に **1〜2件だけ丁寧に**返す。

振り返りシートを組み、`understanding-notes.md` の末尾「## 振り返り」節を**全置換**で書く（追記しない＝二重化回避・

- **Phase 1b-3 の『インプット漏れ』は型欄「インプット漏れ（実行時）」**で1行残す（関係する能力は

  `部分的にできた（あと一段）`＝聞き出せたが反映まで届かなかった）。
- **「並べられていたのに判断を誤った」は型欄「判断（ゲート時）」**で1行残す（乖離や伝達漏れと違い、原因段階は
  ゲートで判断を返した瞬間なので「実行時」ではなく「ゲート時」）。列の埋め方:
  - `何が` = 当該要素（画面の言葉に言い換える・リスト項目名の逐語を出さない）
  - `今回の状態` = `歓迎×修正依頼` は **`部分的にできた（あと一段）`**（要件に無いものを消す筋自体は正しく、

  - `関係する能力` = Phase 5 の紐付けに従う

## Phase 5: レーダー更新（6能力×L0-L3・チャットで確認）

**ここまで（Phase 3 の提示）を終えてから着手する。** 更新フォームの案内を振り返りの冒頭で先出ししない。

**方針（たたき台方式）**: レーダーは「AI が採点する」ものではなく本人の自己評価だが、毎回すべてを一から決めるのは負担が
大きい。そこで **📚 が今回の気づきをもとに6軸の L 値の“たたき台”を提案し、訓練中のコンサルタントは違和感のある軸だけ
チャットで直す**（合意できたら確定）。最終的に本人が納得している点で自己評価の精神は保つ＝提案は (E) PROPOSED、
チャットでの確認が人間ゲートにあたる。**「採点・点数」とは言わない**（あくまで「今回の手応えの下書き」）。

1. **📚 が6軸のたたき台を提案（チャット）** — Phase 1〜4 の気づき＋前回値（`artifacts/_train-profile/radar.json`）を
   もとに、6軸それぞれの L 値（L0〜L3）を提案する。**チャットに小さな表**で出す:
   - 各行 = `能力軸 ／ 今回の提案 L○ ／ （前回 L○）／ 根拠1行`（根拠＝Phase 3 のどの気づきに紐づくか）。
   - 6軸: ビジネス理解 / ヒアリング / 目標設定 / 目利き / 補完 / AI 伝達。
   - 前回値が無い軸（初回）は「（前回 —）」と書き、控えめな提案にする。
   - **根拠1行が書けない軸は L 値を提案せず「据え置き」にする**（数字をでっち上げない＝採点回避）:
     - `ai_communication`（AI伝達）の根拠は **Phase 1c** の結果に紐づける。Phase 1c が「判断材料なし」（入力成果物が
       無い等）なら**前回値据え置き**（初回なら「（前回 —）」のまま提案を控える）。
     - `complement`（補完）は取りこぼし（Phase 1b/1c の抜け）**または「並べられていたのに判断を誤った」の
       `歓迎×修正依頼`**（要件に無いが必要なものだった＝オーナーの意図を補えなかった）が今回出なければ、
       根拠「無し」で**据え置き可**。
       - **『インプット漏れ』区分（Phase 1b-3）は `complement` の根拠に数えない**
         （聞き出せている＝補完の失敗ではないため。これだけなら `complement` は据え置き）。**`ai_communication` の
         マイナス根拠にもしない**（引き継ぎ後に出た情報で、入力時点には存在しなかったため）。
         代わりに **`hearing`（ヒアリング）のプラス側の根拠**に使ってよい（引き継ぎ後も聞き戻せた）。
     - 「並べられていたのに判断を誤った」の紐付け: `NG×容認` / `NG×要件に昇格` → **`discernment`（目利き）**、
       `歓迎×修正依頼` → **`complement`（補完）**。正解2セルは `discernment` の**プラス側の根拠**に使える。
       本区分が0件なら軸提案を動かさない（据え置き規約どおり・数字をでっち上げない）。
     - **`session.json.transcription_mode == "assisted"`（オート記入だった回。未 set / `self` なら通常どおり）は、
       `business_understanding`（ビジネス理解）を据え置きにする** — B/P シートの振り分けを 📚 が行ったため、シートの
       埋まり具合を本人の自己評価の根拠にできない（§前提・入力「シートの扱い」）。
       `hearing`（ヒアリング）は **`dialogue-log.md` の問いの質（掘り方・確認のしかた）を根拠に提案してよい**
       （問いを立てたのは学習者本人であり、そこは設定によらず変わらない）。`goal_setting`（目標設定）は
       **G1・G2 が書かれていればそれを根拠に提案してよい**（目標整理シートは設定によらず学習者が書く欄）。
       **空欄のまま進んだ回は判断材料なしとして据え置く**（この設定では空欄で進めるため＝§phase「目標整理シートの空欄」。
       書かなかったことを低く評価しない）。他の軸は通常どおり。
       - 学習者への言い方は内部用語を出さず「今回は転記をこちらで手伝ったので、シートの整理ぶんは自己評価の材料から
         外しました」まで。**「学習効果が低い設定だった」等の評価は述べない**（採点しない原則・設定は本人が選んだもの）。
     - 提案する軸には必ず今回の気づき起点の根拠を書く。書けないなら据え置き行として「今回は判断材料なし・据え置き」と示す。
2. **確認を1回だけ求める** — 「この**下書き**でよさそうですか？ 違和感のある軸があれば『ヒアリングは L2 に』のように
   教えてください。無ければ『OK』で確定します」と問う（自由入力で受ける・選択肢は配らない）。
   - 直しの指示が来たら該当軸だけ反映し、必要なら一度だけ再提示。往復で粘りすぎない（本人が納得したら確定）。
3. **確定値を radar.json に清書** — `artifacts/_train-profile/radar.json` を Read → merge → Write back で更新する。
   `axes.{軸キー}` に 0-3 を入れる（軸キー: `business_understanding` / `hearing` / `goal_setting` /
   `discernment` / `complement` / `ai_communication`）。
4. **ハンドブックを再生成して結果を見せる** — `skills/train-handbook/SKILL.md` 手順Aで `active_form = "radar_update"`
   （current_step は既に 7）→ 再生成（Write）→ **手順A4 の open 判定に従う**（初回のみ open・2回目以降は Write のみ）。
   確定値がプレフィルされ、チャートが更新される。
   - 案内は短く「順序＋位置」だけ。文型の例:
     > 「では、この内容で能力レーダーを更新しました。開いているハンドブックのタブに戻ると（閉じていたら開き直すと）、
     >  **『← いまここ』**のレーダーで今回の手応えを確認できます。」
   - **ユーザー向け文面でファイル名（`guide.html` 等）を出さない**（「ハンドブック」と呼ぶ）。位置は必ず
     ハンドブック側の現在地マーカー **「← いまここ」** で示す。
   - 手動で直したい人はハンドブックのフォームで直して貼り戻してもよい（任意・チャット確定が主経路）。

完了で `step7_state = "radar_updated"`。各気づきには「これは〈能力軸〉の L○相当の動作（できた／あと一段）」を
一言添えると、提案の根拠が腹落ちする（Phase 3 の提示と一貫させる）。

## 完了後

  `app_name` で特定）を Read → merge → Write back で **`completed:true` ＋ `completed_at` に更新**する（新規 append しない。
  万一 entry が無ければ 1 件だけ append）。再走時のネタバレ注記の判定材料。

  **一切足さない**（phases/train §「受け手は常に訓練中のコンサルタントだけ」ガード。末尾は最も漏れやすいので明示）。
