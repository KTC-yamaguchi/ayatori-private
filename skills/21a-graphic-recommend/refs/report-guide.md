## §2 カテゴリ帯 → グラフィック期待度の固定対応表

LLM の裁量は「本プロジェクトがどの帯に入るか」の分類**のみ** (期待度と推奨の対応は表で固定)。
境界事例で表の更新が必要になったら retro (Phase 4 / 6) で本表を改訂する (実現可能性検証の調査 §8-2)。

| カテゴリ帯 | グラフィック期待度 | 既定の推奨 | 例 |
|---|---|---|---|
| ゲーム / 子供向け・教育 / エンタメ | 高 — キャラクター・イラストが期待される | 強く推奨 | ゲームアプリ、読み聞かせアプリ |
| B2C 生活系（健康・家計・旅行・EC） | 中 — オンボーディング・空状態等の要所で期待 | 検討推奨 | 家計簿アプリ、ヘルスケア |
| 実用ツール / 業務効率 / ダッシュボード | 低 — ピクトグラム中心で十分 | 不要 | 運転支援ツール、業務管理 |

補正規則 (表の適用後に確認する):

- **確信度**: カテゴリ引用根拠が明確 + illustration_policy と整合 → 高。引用は取れるが帯の境界事例 → 中。それ以外 → 低。
- **design-brief.yaml による補正 (存在する場合のみ)**: `common.hearing` の `tone_mood` / `brand_direction` /
  `avoid_styles` は Phase 2 で確定済みの (A) CONFIRMED prior — illustration_policy と同様に確信度・整合の
  材料に使う (推奨の方向性と整合 → 確信度を補強 / 矛盾 → 確信度を 1 段下げて 2-3 節に明示)。
  **不在時は補正なしで表どおり** (fail-open — 不在を確信度の減点材料にしない)。判断軸は引き続き
  「カテゴリから推定されるユーザーの期待」のみ — design-brief を新しい判断軸に昇格させない。
  illustration_policy と同じく **§4 の候補列挙を抑制する材料にもしない**。
- 期待度「低」でも、オンボーディング説明等に**任意オプション** 1 件程度を「1. 推奨（結論）」の
  任意オプション行 + §4 候補一覧に載せてよい (推奨自体は「不要」のまま — sunpark サンプルと同型)。
- **`illustration_policy` の適用範囲**: `pictogram` は「**アイコンをどう描くか**」
  の様式選択であり、**コンテンツグラフィック (イラスト/写真) の要否とは別軸**。総合推奨 (結論) の
  整合材料に使うのはよいが、**§4 の候補列挙を抑制する材料にしてはならない** (候補の絞り込みは
  21b 人間ゲートの役割)。

## §3 統制規約 (LLM の想像への堕ち防止 — 4 か条)

1. **根拠引用の必須化**: カテゴリ判定 (2-1 節) には `requirements/00-raw-input.md` /
   `requirements/01-overview.md` からの**逐語引用**を必須とする (Operating Principle 3 の引用義務と同型)。
   引用が 1 件も出せない場合は判定不能 → §5 の inventory-only degrade に落とす (推測での決め打ち禁止 —
   Operating Principle 4)。
2. **裁量は帯分類のみ**: 期待度・既定推奨は §2 の表から機械的に引く。表にない第 4 の帯や
   独自の期待度を発明しない。
3. **曖昧時は両候補併記** (P4-01 準拠): カテゴリ解釈候補が N≥2 に割れたら (例: 教育×ゲームの
   ハイブリッド)、決め打ちせず**両候補と両推奨を 2-1 / 2-2 節に併記**し、「1. 推奨（結論）」は
   保守的な側 (期待度の低い側) を主推奨 + もう一方を併記する。ここで AskUserQuestion は
   **発火しない** — レポート自体が人間ゲート (21b Q1) の直前提示物なので、質問はゲートに委ねる
   (P4-07 二重質問禁止)。
4. **illustration_policy との整合チェック**: 推定期待度と Phase 1a の選択が矛盾する場合
   (例: policy=pictogram だがカテゴリ=ゲーム) は 2-3 節で「**矛盾を検出 — illustration_policy の
   再考を推奨**」と明示し、「1. 推奨（結論）」にもその旨を 1 行載せる (矛盾の隠蔽・無言調整は禁止。
   これは本機能の付加価値でもある)。

## §4 候補スロットの洗い出し規約

- **スロット種別の固定語彙 (レポート内部の分類)**: `onboarding_explainer` / `empty_state` /
  `error_state` / `success_celebration` / `hero_brand` / `mascot` / `content_media`
  (実現可能性検証の調査 §5 の enum 案)。
  表には日本語の説明 (例: 「オンボーディング説明」) を添えてよいが、種別自体はこの語彙から選ぶ
  (レポート間の表記ゆれ防止)。**機械可読の下流契約ではない** — `graphic-plan.schema.json` に
  対応 field は存在せず、21b は本表を人間可読の参考材料として候補洗い出し (hearing-guide §3 の
  自由記述観点) に使うのみ。将来 slot に `slot_type` field を追加する場合は本語彙を種にする (拡張点)。
  v1 では `empty_state` / `error_state` は対象画面が存在しない (main のみ — §1 の注記を必ず載せる)。
- **`illustration_policy == illustration_character`**: inventory の `illust_placeholders`
  (`data-scene` 付き) を**そのまま候補スロットにする** (LLM 裁量ゼロの直取り — 調査 §4-4 ケース B)。
- **`role="img"` の意味視覚 (meaningful_visuals) は候補にしない** — §1 の「5. 分析対象外」に列挙する。
- **網羅列挙**: 候補は「載せるか迷ったら載せる」。レポートは (E) PROPOSED で
  絞り込みは 21b 人間ゲートの役割のため、過剰列挙の害 (表が 1 行増える) より**漏れの害の方が大きい**。
  代わりに個別推奨 3 値 (必須級 / 推奨 / 任意) で優先度を細かく付け、**表は優先度順に並べる**
  (「少なく厳選」で調整しない — 調整は tier で行う)。
- **§3-b の ② (グラフィック代替候補) は必ず §4 候補に昇格する**: 同一 parent_class のグループは
  1 slot にまとめる (例: アクション一覧のサムネイル列 ×5 = 1 slot、anchor は `class:{parent_class}`)。
- 候補 0 件の場合は §4 節に「候補なし」と明記する (空表を出さない)。
- **絵文字シグナルは粗い heuristic**: `emoji_in_markup` は正規表現ベースの検出で (★✓✔ 等の頻出記号は
  script 側で除外済みだが網羅的ではない)、これを根拠に「illustration_policy と不整合」と書く前に
  `screens_with_emoji` の該当画面で実際の文字を目視確認する。確認できない場合は「不整合」と
  断定せず「絵文字らしき文字を検出 (要確認)」に留める。
- **個別推奨はスロット種別 × 期待度帯の固定対応表から引く** (§2 と同じパターン — LLM の裁量は
  種別分類のみ。表と異なる tier を裁量で付けない。逸脱が妥当に見える境界事例は retro (Phase 4 / 6)
  で本表そのものを改訂する):

  | スロット種別 | 期待度 高 | 期待度 中 | 期待度 低 |
  |---|---|---|---|
  | `onboarding_explainer` | 必須級 | 推奨 | 任意 |
  | `empty_state` / `error_state` | 必須級 | 推奨 | 任意 |
  | `hero_brand` | 必須級 | 推奨 | 任意 |
  | `success_celebration` | 推奨 | 推奨 | 任意 |
  | `mascot` | 推奨 | 任意 | 任意 |
  | `content_media` | 推奨 | 任意 | 任意 |

  期待度「低」帯が全種別で任意止まりなのは生成コスト (gpt-image-2 は低速・有料) を踏まえた既定。
  1 行理由には「なぜこの箇所か」(表の根拠は書かなくてよい — 表自体が根拠) を書く。
  表の既定 tier の**上書き判断は 21a では行わない** (例: 入力タスク画面だがブランド初回接点、等の
  例外昇格) — override 層は 21b 人間ゲートが担う (レポートは (E) PROPOSED、21b は多選 + 自由記述で
  候補の追加・昇格が常時可能)。
- **既存グラフィックとの重複回避 (決定的)**: inventory で当該箇所に既にグラフィックが入っていると
  分かる場合 — `meaningful_visuals.kind == "illustration_canon"` (イラスト正典の署名一致) /
  `raster_imgs` (実画像) — は候補にしない (重複推薦の抑止)。既存画像の**差し替え**提案は 21b の
  自由記述 (人間発意) に委ねる。`illust_placeholders` は「まだ入っていない」マーキングなので
  本規則の対象外 (従来どおり直取り)。
- **負の規則 (候補にしない画面)**: フォーム入力 / 決済 / 認証 (ログイン・サインアップ・OTP 等) の
  **入力タスク画面**は、大型グラフィックがタスク完遂を阻害する (UX 定石) ため候補にしない —
  カテゴリ帯が高くても同じ。判定は**画面のタスク性**で行う (同じ Finance でも送金入力 = 候補外 /
  口座開設完了 = `success_celebration` 候補)。除外した画面は §1 の「5. 分析対象外」に列挙する。
  入力タスクの**外側** (完了画面・空/エラー状態・オンボーディング) は通常どおり候補にできる。

## §5 degrade 書式 (inventory-only レポート — 設計 §8-4 / 調査 §7)

カテゴリ判定材料の欠損 (`category_material_available == false`、リバース経路等) または
§3-1 の引用不能時は、**推奨を出さず**次の形に degrade する (fail-open — エラー停止しない):

- 「1. 推奨（結論）」の表を次で置き換える:

  ```markdown
  | 判定 | 値 |
  |---|---|
  | 推奨 | ※ 不明 (unknown) — カテゴリ判定材料 (requirements/00-raw-input.md 等) が不足のため提示なし |
  | 次回 ask 対象 | アプリ/コンテンツのカテゴリ (Step 21b のヒアリングでユーザー判断) |
  ```

- 「2. 分析根拠」は「判定材料不足のため省略 (※ 不明 (unknown))」の 1 行のみ。
- 「3. 画面インベントリ」「4. 候補スロット」「5. ガードレール」は通常どおり出力する
  (インベントリは決定的抽出 (C) DERIVED なので材料欠損の影響を受けない)。§4 に候補が
  1 件以上あるなら slot-anchors + 視覚レポート (§7) も通常どおり生成する。
- 21b は `mode == report` のままレポートを提示し、推奨行の「※ 不明」を含めて要約する
  (レポートなしの `mode == plain` とは別状態)。

## §6 Operating Principle 4 の分類ラベル (書き分けの根拠)

| 部 | 分類 |
|---|---|
| 1. 推奨（結論） | (E) PROPOSED — 必ず 21b 人間ゲートを通る |
| 2. 分析根拠 | 判定は (E)、逐語引用は (A) CONFIRMED、期待度導出は (C) DERIVED (導出元 = §2 の表) |
| 3. 画面インベントリ | (C) DERIVED (決定的抽出 — script 出力の転記) |
| 4. 候補スロット一覧 | (E) PROPOSED (個別推奨の既定値は §4 固定表からの (C) DERIVED — 導出元 = 種別 × 期待度帯) |
| 5. 分析対象外（ガードレール） | 事実の列挙 (inventory 由来) + 判断軸の明記 |

2-1 節見出しの `※ 推測 (inferred)` マーカーは固定で残す (カテゴリ判定は引用に基づく推測であり
確定事実ではない、の明示 — CLAUDE.md Operating Principle 4 マーキング規約)。

## §7 視覚レポート (graphic-recommend.html) の anchor 規約 — 2 ファイル構成

§4 の候補スロットを実際の画面プレビュー上で「ここが画像生成の候補箇所です」とハイライト表示する
派生 HTML (**MD = 分析詳細のテキスト / HTML = 見た目で判断** — Producer 提案 Confluence 4061397312、
Manager FB「グラフィックなので見た目がないと判断しずらい」への対応)。HTML の生成は決定的 script
(`scripts/render-recommend-html.mjs`) の責務で **手焼き禁止** (`render-color-report.mjs` と同じ線引き)。
LLM の責務は §4 に **slot-anchors コメント** (§1 の固定構造の一部) を書くことだけ。

- **書式**: §4 の表の直後に `<!-- ayatori:slot-anchors {json} -->`。`slot_anchors[].n` は §4 表の
  `#` と一致させる。候補 0 件 (「候補なし」) のときは書かない (script も HTML を生成しない)。
  JSON 内の文字列に `-->` を含めてはならない (HTML コメント終端と衝突)。
- **anchor 語彙 (3 種 + 省略)**:

  | anchor | script の解決方法 | 使いどころ |
  |---|---|---|
  | `icon:{name}[:{nth}]` | `icons/{name}.svg` の形状署名一致 (nth 省略 = 全出現をハイライト、nth は代表ファイル内の文書順 1 始まり) | inventory の `icons_used` にある要素。`icon_occurrences` が 2 以上 (ナビ等で繰り返される icon) は nth 指定か `text:` に切替える |
  | `scene:{data-scene}` | `illust-placeholder` の `data-scene` 直取り | `illustration_policy == illustration_character` の既存 placeholder スロット |
  | `text:{逐語文字列}` | 画面 HTML 内で**一意に 1 回**出現する逐語文字列の包含タグ | 既存要素がない箇所 (「進捗ヘッダー上」等)。近傍見出しのテキストや `class="..."` 逐語が使える |
  | `class:{token}` | class 属性に token を持つ**全要素**をハイライト | グループ slot (§8 ② のサムネイル列等)。token は `icon_contexts` の `parent_class` から取る |
  | (省略 / entry なし) | 画面全体プレビュー (リングなし) に fail-open | 位置を機械特定できない場合。無理に発明しない |

- **text: の逐語根拠 (統制 §3-1 と同型)**: 文字列を想像で書かない — 対象画面 HTML への
  **targeted Grep (該当スロット画面のみ・行単位)** で「実在 + 一意 (1 回)」を確認してから書く。
  HTML 全文の Read はしない (extract-inventory の context 保護設計を崩さない)。一意が取れない
  場合は anchor を省略する (script 側も一意 1 件のみ解決する — 決め打ちしない)。
- **fail-open**: anchor 解決不能・script 非 0 exit でも 21a は停止しない (SKILL.md Step 2b の
  routing)。解決不能スロットはリングなしの画面プレビュー + 理由表示に degrade する。

## §8 アイコン用途の 2 分類規約 (① 機能アイコン / ② グラフィック代替候補)

「ピクトグラム中心 (illustration_policy=pictogram)」は**アイコンの様式選択**であり、画面内の全アイコン
使用箇所が「アイコンのままが望ましい」ことを意味しない。`icon_contexts` (extract-inventory が返す
決定的特徴量: `px` = CSS 表示サイズ推定 / `parent_class` / `siblings` = 同型コンテナ数 / `in_nav` /
`in_control`) を材料に、各使用箇所を 2 分類し §1 の 3-b 節に記録する:

| 判定 | signal (機械的特徴量) | 典型例 |
|---|---|---|
| **② 代替候補** (グラフィック化を §4 で提案) | `px >= 40` かつ `in_nav` でない — 拡大表示 = アイデンティティ / コンテンツの代役。**`in_control` は否決材料にしない** (一覧カード全体が `<a>` のレイアウトでは、カード内のコンテンツサムネイルも `in_control=true` になるため。操作グリフ [chevron / 戻る] は小サイズなので px 条件で自然に除外される) | ロゴ位置の拡大アイコン、詳細画面の表題アイコン、アバター placeholder、リンクカード内の大型サムネイル |
| **② 代替候補** (グループで 1 slot) | `siblings >= 3` かつ `in_nav` でなく `px >= 24` — 同型コンテナのサムネイル列 = コンテンツ代役 (同じく `in_control` は否決材料にしない) | 一覧リストの項目先頭アイコン群、特徴バレットの飾りアイコン群 |
| **① 機能アイコン** (据え置き・候補にしない) | `in_nav`、または `px <= 32` の単独アイコン (control 内の chevron・戻る・フォーム項目を含む) — 操作・状態表示の UI 部品 | ボトムナビ、chevron、フォーム項目アイコン、戻るボタン |
| ① に倒す (保守) | `px` が推定不能等で判定材料不足 | — (必要なら「要確認」を注記) |

- 境界事例 (例: siblings 3 だが純装飾) は **② に倒す** — 候補に載せて 21b の人間判断へ回す方が
  漏らすより安全 (網羅列挙の原則、§4)。
- ② の個別推奨は **§4 の固定対応表から引く** (種別対応の通常形: 単独のアイデンティティ代役 →
  `hero_brand` / サムネイル列・バレット飾り → `content_media`)。1 行理由には生成コストと情報密度への
  影響を書く。
- ① は §4 に載せない (ガードレールの「コア UI」とは別区分 — ① は「アイコンで正しい」箇所)。
