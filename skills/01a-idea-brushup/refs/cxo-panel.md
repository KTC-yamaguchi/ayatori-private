# cxo-panel: CxO 視点ミニ批評

Step 4 (CxO 視点ミニ批評) の実行手順書。9 役の CxO ペルソナからパネル (3〜5 席) を
席構造で組み、各席が 1 回ずつ静的批評 (良い点 1 + 懸念 1〜2 + 問い 1) を
行い、全懸念へのユーザースタンスをリアクションゲートで確定させる。
翻案元: `kinto-dev/idea-explorer` の roundtable ペルソナ群
(`backend/prompts/roundtable/personas/*.md` — 各ペルソナ全文の翻案。専門語彙リスト・
相場円額・討論作法・企業固有前提のみ除外)。相互討論型ラウンドテーブルの資産から
**視点の多様性だけ** を移植した静的批評版。ペルソナ brief 本体は
`skills/01a-idea-brushup/refs/personas/` 配下の 9 ファイルに分割保持する
(下記「9 ペルソナ brief の参照」)。

## 共通制約

- **相互討論はしない**: 各ペルソナは他ペルソナの発言に言及・反論・同調しない。
  1 回ずつの独立した批評のみ (討論の連鎖・ファシリテーター進行は移植対象外)。
- 発言は自分の担当領域からのみ。**盲目的な賞賛の禁止** — 良い点も自分の判断軸に
  照らして実質のある 1 点を挙げる (お世辞・網羅的な称賛はしない)。
- 批評の入力は「現在のアイデア像 5 軸 (Step 3 確定版) + ここまでの対話ログ」のみ
  (resume 時は前ラウンドの brief ③④⑤ も含む)。
- 各ペルソナ brief の数値閾値は **スタートアップ事業想定の目安**。社内ツール・PoC 等の
  アイデアでは規模を読み替える (例: 収益 → 工数削減価値、顧客獲得 → 利用部門への浸透)。
- 批評・懸念・問いはすべて **(E) PROPOSED** — 確定事実ではなく AI 提案であり、
  リアクションゲートのユーザースタンスを経て初めて先へ進む。

## ※未検証 (web 検索なし) の付与規則

市場規模・競合製品名・相場・業界動向・法規動向・補助金 / 税制等の制度名への言及には、
良い点 / 懸念 / 問いの別を問わず `※未検証 (web 検索なし)` を付与する (SKILL.md・
brief テンプレート ⑦ と同一リテラル)。マーカーの意味は「web 検索で裏取りしていない」—
**ユーザー由来の競合言及にも付く** (真偽の検証は本スキルの責務外であり、7 軸以降にも
持ち越される)。

ペルソナ brief 由来か否かで判定する (検証可能な単一基準): **ペルソナ brief 記載の
判断閾値・目安をそのまま物差しとして使う場合はマーカー不要** (スタートアップ想定の
目安として意図的に保持された値 — 共通制約の読み替え規約が掛かる)。**ペルソナ brief に
無い数値・固有名詞を AI が自分の知識から挙げる場合は必ず付与する**。

## パネル構成と選定ルール (3〜5 席)

パネルは固定の席構造で組む。「関連する 3 役を選ぶ」のではなく、**アイデアが答える
べき 3 つの独立した問い (誰に価値があるか / 作れるか / 商売として立つか) に 1 席ずつ
+ 該当時のみ守り枠** という構成。選定は批評の正しさの判定ではなく、ユーザーの注意
予算 (リアクションゲートで取るスタンスの件数) の配分である。

本節の通常構成は **5 軸充足ゲート (`refs/converge-specify.md` § 3-5) 通過が前提**。
未充足のままユーザーが実施を明示選択した場合も本手順をそのまま適用する
(下記「未充足のまま強行する場合」— 席の決定手順・席数は削減せず、創作しないことを
優先して懸念件数のみ規定に届かなくてよい)。

### 席の決定手順 (上から順に機械的に適用)

**席 1 (価値枠)**: CPO — 無条件で常設。判定不要。

**席 2 (実現枠)**: アイデアの How に技術要素 (AI / LLM / OCR / 機械学習 /
大規模データ処理・データ基盤 / 外部 API / デバイス・センサー連携) が 1 つでもあれば
**CTO**、なければ **CEO** を実行代表として登用する。単純な登録・一覧・集計だけの
アプリは技術要素に数えない (その場合の実行の論点は段取りとリソース = CEO の領分)。根拠を逐語引用すること (引用できなければ「技術要素なし」=
CEO)。

**席 3 (事業代表枠)**: 事業ブロック {CEO, CMO, CFO, CSO, CRO} から 1 役 (席 2 で
CEO を登用済みの場合、CEO はこの予選から除外)。予選手順:

1. ブロック各役について、下記シグナルがアイデア記述 (5 軸 + 今回の核) に根拠を
   持つか判定し、発火役を列挙する。根拠は**逐語引用必須** (引用できなければ発火
   なし)。**同一の引用で複数役が発火する場合は、記載順先頭の役の発火として扱う**
   (どちらを採っても同ブロックの視点は保たれるため、機械的に倒す)。
2. 発火役のうち、引用が「今回の核」の記述文から取れている役 (= 核由来) があれば、
   その中から核に最も直接関係する 1 役を採る。迷ったら記載順の先頭。
3. 核由来の役がなければ、発火役から「今回の核」との関連が最も強い 1 役。迷ったら
   記載順の先頭。
4. 発火役がゼロなら CEO (席 2 で CEO 登用済みなら CMO)。

| 役 | 事業ブロックのシグナル |
|---|---|
| CEO | 新規事業・立ち上げの文脈、リソース配分・優先順位・「何を捨てるか」が論点 |
| CMO | Who が一般ユーザー (社外) の獲得・集客・市場投入の文脈、WhyNot に競合の話が濃い |
| CFO | コスト・予算・運用費・収支への言及がある |
| CSO | WhyNot が弱い / 競合が多い領域・参入タイミング・持続的優位が論点 |
| CRO | What / How に課金・価格・マネタイズが含まれる |

**席 4・5 (守り枠、条件付き)**:

- **CLO**: 個人情報・位置情報・決済・未成年を扱う、または規制業種 (金融・医療・
  運輸等) に接触する根拠があれば設置。
- **CIPO**: 独自アルゴリズム・データ資産・OSS 利用・コンテンツ権利が核にある根拠が
  あれば設置。
- 根拠は逐語引用必須。両方発火なら両方設置 (5 席)。どちらも発火しなければ守り枠
  なし (3 席)。**引用は取れるが該当するか解釈が割れる場合は着席させる (安全側)** —
  過剰な 1 席は許容し、リスク視点の見落としを避ける。

記載順 = CEO → CTO → CPO → CMO → CFO → CSO → CRO → CLO → CIPO (正本は
「9 ペルソナ brief の参照」の一覧表)。

Step 4 は毎ラウンド実行されるため、席の決定も毎ラウンドこの手順で行う。前ラウンドと
同一の顔ぶれになってもよいが、決定根拠は毎回明示する。前ラウンドでスタンス確定済みの
懸念は、アイデア像の変化で前提が崩れた場合を除き再提示しない (確定済みスタンスは
brief ⑤ を参照)。

> 守り枠発火時はパネルが 4〜5 席になり、SKILL.md Step 4 の「3 ペルソナ」表記より
> 席数が多くなる — 守り枠は本 ref 固有の拡張として明示する (SKILL.md 側の追従は
> 契約改版として別途)。

### 席の表示フォーマット

批評に入る前に、次の形式でパネル構成と根拠をユーザーに明示する
(📍 は付けない — 📍 は質問の冒頭専用):

```
今回のパネルは {N} 席です。
- 価値枠: CPO (常設)
- 実現枠: {CTO または CEO} — {技術要素の引用、なければ「技術要素なし」}
- 事業代表: {役} — {発火シグナルと引用 1 行}
- 守り枠: {役} — {引用 1 行} (設置時のみ。なければこの行を出さない)
```

## 未充足のまま強行する場合 (5 軸未充足時の例外運用)

Step 3 の 5 軸充足ゲート (`refs/converge-specify.md` § 3-5) で未充足軸が残ったまま、
ユーザーが「未充足のまま批評を受ける」を明示的に選択した場合の運用。**既定の解決策には
しない** — ゲートの既定動作は補完質問で軸を埋めることであり、推奨は批評 skip。強行は
ユーザー希望時に限る例外処理。

- **パネル構成は通常どおり** — 席の決定手順・席数は削減しない (縮退パネルは
  設けない)。削減してよいのは懸念件数のみ (下記「創作しないことを優先する」)。
- **席の予選での未充足軸の扱い**: 軸本文がリテラル `※不明 (unknown)`、または
  `[proposal]` 付きの AI 補完のみの場合、そのテキストはシグナルの逐語引用として
  扱わない (= その軸からは発火なし)。結果として発火役がゼロになる場合は通常どおり
  予選手順 4 の fallback (CEO / 登用済みなら CMO) で閉じる。
- **創作しないことを優先する** — 未充足軸を根拠にした懸念は立てない (材料が無い軸への
  批評は創作になる。「創作で埋めない」原則)。その結果、懸念が規定件数 (1 席あたり
  1〜2 件) に届かない場合も、件数を無理に満たさない — 強行を選んだユーザーに追加の
  回答を求めて枠を埋めることもしない。未充足軸については懸念ではなく **問い** で
  その軸の言語化を促す。
- **懸念 0 件を許容する**: 席の判断軸が未充足軸と重なり、充足軸の材料から懸念を
  1 件も立てられない場合は、創作してまで発言フォーマットの「懸念 1」を埋めない —
  懸念枠を未充足軸への問いに置き換えてよい (問いは未充足軸ごとに増やしてよい)。
  創作防止がフォーマット遵守に優先する。
- brief ⑤ への記録は `refs/idea-brief-template.md` § ⑤ の強行時規定に従う
  (冒頭に未充足軸を 1 行明記)。

席の表示は通常フォーマットの 1 行目のみ次の形に置き換え、未充足のままの実施で
あることを明示する:

```
今回のパネルは {N} 席です — 未充足軸あり: {軸名, …}
```

## 発言フォーマット

各ペルソナは次の構造で 1 回だけ発言する (各項目 1〜2 文):

```
### {役} (選定理由: {1 行})
- 良い点: {1 件}
- 懸念 1: {何が危ういか + 根拠となる自ペルソナの判断軸}
- 懸念 2: {同上 — 独立した判断軸に基づく場合のみ}
- 問い: {ユーザーが次に確認・言語化すべきこと 1 件}
```

- 懸念を 2 件にするのは **独立した判断軸に基づく場合のみ**。同一判断軸に還元できる
  懸念は 1 件に統合する (水増しも切り捨てもしない)。
- 例外: 未充足のまま強行する場合に限り、懸念 0 件 + 問い置換を許容する (規定は
  「未充足のまま強行する場合」節)。通常ラウンドでは懸念 1 件以上が必須。
- 問いは「次の一手」として立てる — 指摘で終わらせず、何を確認・言語化すれば懸念が
  晴れるかを問う (翻案元 common-guidelines「指摘には対策案 or 検証方法をセットで」の
  静的批評版)。
- ペルソナ brief の「必ず提示 / 明示する」系の癖 (人間の宿題・代替案・見積もり取得先) は、
  **懸念または問いの文中に 1 句で畳む**。別立ての項目・段落を追加しない (各項目
  1〜2 文の構造を維持する)。
- スタートアップ想定の閾値を読み替えて適用した場合は、懸念・問いの文中に読み替え後の
  尺度を明示する (例: 収益 → 工数削減価値)。
- brief ⑤ への記録はこの見出し構造のまま行い、リアクションゲート後に各懸念へ
  「→ ユーザー: …」、問いへ「→ 回答: … (または ※不明)」を追記する
  (書式の SoT は `refs/idea-brief-template.md` § ⑤)。
- template ⑤ との既知の差分 2 点 (本 ref 固有の運用として明示。template 側への反映は
  契約改版 [4 タスク周知] として別途): (a) 懸念が 2 件のときは `懸念 1:` / `懸念 2:` の
  番号付きラベルで書く (1 件なら `懸念:`)。(b) スタンス値には template の 2 値に加え
  「判断保留 (③ 参照)」の第 3 値がある (リアクションゲート手順 4 (b) 参照)。

出力例:

```
### CTO (選定理由: How が外部カレンダー API 連携を核にしているため)
- 良い点: 機能が 3 つに絞れており、PoC 6〜8 週で動く形にできる見立てが立つ。
- 懸念 1: 予定データの取得が外部 API 1 本に依存し、障害時の代替経路がない
  (外部依存は SLA と切り替えやすさの両面で見る、が私の判断軸)。
- 問い: その API が丸 1 日止まったとき、ユーザーに何をどう見せるかは決まっているか?
```

## リアクションゲート (idea-explorer #265 の翻案)

**原則: 全懸念に「そう思う / そうは思わない」の 2 択スタンスを取らせる (中立なし)。**
全懸念の処遇 (そう思う / そうは思わない / 判断保留 → ③ 記録) が確定するまで Step 5 に
進まない (判断保留は ③ に記録済みであれば「未回答」ではない)。

手順:

1. **方式の選択**: 全席の批評をすべて提示し終えてから懸念総数 (3〜10 件) を数え、
   ゲート方式を選択する。提示の途中でゲートを差し込まない (方式の混在禁止)。
2. **懸念計 4 件以下 — ペルソナごとに 1 AskUserQuestion**:
   - 1 呼び出しに、そのペルソナの懸念数ぶんの質問 (1〜2 問) を入れる。
   - 各質問: question 文頭に `📍 Round {N}/3: CxO Panel — {役} reaction`、本文は懸念の
     要約。header はペルソナ略称ベース (例: `CTO 懸念1`)。
   - option は 2 つ固定 (提示上はこれに自動付与の "Other" が加わる — SKILL.md
     § Interaction Style): 「そう思う」(懸念は妥当 — 次の検討材料にする) /
     「そうは思わない」(自分の考えと違う — 理由は次ラウンドの種にできる)。
   - 各質問が 2 option 固定のため「1 質問あたり 2〜4 option」の制約を常に満たし、
     質問数も 1〜2 問で「1 呼び出し最大 4 質問」の制約内に収まる (質問間で option 数を
     合算する制約は存在しない)。
3. **懸念計 5 件以上 — plain chat fallback**: 下記「fallback の提示・返信書式」に従って
   全懸念を一括処理する。書式の SoT は `skills/01b-add-feature-question/SKILL.md`
   § Plain chat fallback — 下記は SoT の再掲 + 本ステップ固有の運用であり、再掲との
   ズレが疑われる場合のみ 01b を Read して優先する (毎回の全文 Read はしない)。
4. **Other / 保留の処理**:
   - (a) 「もう 7 軸へ進みたい」系 → SKILL.md § Interaction Style の共通 escape hatch へ。
   - (b) 「わからない・判断できない」系 (Other 回答・fallback の「保留: n」共通) →
     偽スタンスを付けない。brief ③ 未解決の論点へ `※不明 (unknown)` + 次回 ask 対象
     キー (`idea_brief.{key}`) 併記で記録し (③ の行書式は
     `refs/idea-brief-template.md` § ③ に従う)、⑤ の当該懸念には
     「→ ユーザー: 判断保留 (③ 参照)」と書く。
   - (c) スタンスが読み取れないその他の Other → 該当懸念のみ再質問する (1 回まで。
     なお読み取れなければ (b) の保留として扱う)。
5. **問いへの回答 (任意)**: スタンス確定後、全席の問いを番号付きでまとめて 1 回
   plain chat で提示し、「答えられるものだけで構いません (スキップ可)」と添えて受領
   する。未回答の問いは brief ⑤ に「→ 回答: ※不明」と記録する。
6. **記録と born-resolved の境界**: Step 4 が記録するのはスタンスと問いの回答のみ。
   「そう思う」が付いた懸念への **対応方針** は、ユーザーが問いへの回答やコメントで
   明示した場合に限り born-resolved の対象になる (Step 4 から対応方針を聞く新規質問は
   発行しない)。**対応方針が示されなかった「そう思う」懸念は未解決として扱い**、
   brief ③ 未解決の論点へ `※不明 (unknown)` + 次回 ask 対象キー (`idea_brief.{key}`)
   併記で記録する (行書式は手順 4 (b) と同じく template § ③ に従う。SKILL.md § P4
   「未解決のまま残った懸念」の実装。⑤ は最終ラウンドで上書きされるため、③ に
   記録しないとパネル交代時にハンドオフから消失する)。
   born-resolved の定義・手順は SKILL.md § Operating Principle 4 準拠 (P4)
   に従う (本 ref では再定義しない)。

### fallback の提示・返信書式

書式の SoT は 01b。以下は本ステップ固有の運用:

```
📍 Round {N}/3: CxO Panel — Stance check
パネル {席数} 席の懸念は計 {M} 件です。以下に通し番号で列挙します。
1. [CTO] {懸念の要約}
2. [CTO] {懸念の要約}
3. [CPO] {懸念の要約}
...

選択方法: 「そう思う」に該当する番号をカンマ区切りで返信してください (例: 「1, 3」)。
挙げなかった番号は「そうは思わない」として記録します。
判断を保留したい番号や自信が持てない番号は、無理に分類せず「保留: 2」の形で
書き添えてください (未解決の論点として brief に残します)。1 件も「そう思う」が
なければ「なし」と返信してください。
```

- 受領後、確定スタンス表 (番号 | 役 | 懸念要約 | スタンス) を **表示のみ** で
  echo-back する (追加の承認質問にしない)。誤りがあればユーザーは plain chat で訂正
  でき、訂正はそのまま表に反映して再表示する。

## 9 ペルソナ brief の参照

各ペルソナの brief は `skills/01a-idea-brushup/refs/personas/` 配下の 9 ファイルに
分割して保持する (翻案元の判断軸・問い・NoGo を全量保持した版)。**席に着いた役
(3〜5) のぶんだけ Read する** — 席に着かない役の brief は読み込まない (席の決定は
上記手順と下記一覧だけで完結する)。Read のタイミングは「席の表示後・批評の生成前」。
同一セッションで Read 済みの brief は再 Read しない (コンテキストに残存しているものを
使う)。Read した brief に Preamble の stub ガードと同じ未実装マーカーが残っている
場合は批評を生成せず、同ガードと同じ文言で中断する (ペルソナの即興創作を防ぐ)。

  同一引用の複数発火・守り枠の tie-break はこの順で決める。
- 表の「人物一言」は各 brief 冒頭の人物像の **要約** であり、正本は brief 側
  (逐語同期は要求しない)。
- 各 brief は固定セクション構成 (担当領域 / 重視する観点 / 判断軸と閾値 / 規模感の
  勘所 / 典型的な問い / 対立しやすい相手と論点 / `NoGo / 撤退ライン` / 人格と口調 /
  思考スタイル)。
  批評は Read した brief の判断軸から、当該アイデアに最も関係する軸を選んで行う
  (全軸を網羅的にコメントしない)。
- `NoGo / 撤退ライン` は本フェーズでは **該当判定に使わない**。アイデアを固めに来た
  現段階の未調査・未検証を NoGo 該当とみなさず、「その線を将来越えないために今何を
  言語化すべきか」という懸念・問いの材料としてのみ用いる (事業の Go / NoGo 判定は
  本スキルの責務外 — maturity-check「8 軸 → 6 軸」の理由と同じ整理)。
- 「対立しやすい相手と論点」は選定の機械規則には使わない — 視点の独立性の明示と、
  批評を読むユーザーへの背景情報として保持する。ペアは各 brief の代表 4 件で、
  相手側 brief に同一ペアが載ることは保証せず、論点表現も各ペルソナの視点で異なりうる
  (翻案元と同じ非対称構造 — 対称性は要求しない)。
- 相場性の数値 (広告単価・補助金上限額・専門家費用 等) は brief 側で概念化してある。
  批評で具体額に触れる場合は自分の推定であることを自覚し、必ず
  `※未検証 (web 検索なし)` を付す (付与規則は上記 § 参照)。
