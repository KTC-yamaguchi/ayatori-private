# AI/人間タグ分類ルール v0.1（要件採点）

> **R&D-1 成果物**
> ④ AI採点で各 `deficiency` に付与する **AI 改善可能 / 人間対応必要** タグの分類ルール。
> AYATORI仕様書 §4 ⑭（デザイン採点）のタグベース手法を要件採点側へ翻案。

---

## 背景

AYATORI仕様書 §4 ⑭ では、デザイン採点（⑭）の各減点項目に以下のタグを付与する：

| タグ | デフォルト対象 | 意味 |
|------|------|------|
| `AI改善可能` | Layer 1（技術・数値）・Layer 2（ユーザビリティ） | AIの再生成で改善見込み |
| `人間対応必要` | Layer 3（デザイン性・センス） | 人間の判断・修正が必要 |

⑮ ループ制御は `current.ai_improvable_deductions == 0` を合格条件とし、**AI が解決できる減点をゼロにすること** をゴールとする。

**要件側（③④⑤）には現在タグの概念がない**。⑤ は `total >= 80` の閾値判定のみ。
本ルール v0.1 は要件採点側にも同じタグメカニズムを導入するための提案である。

---

## なぜ要件側にもタグが必要か

現在のループ動作:
- ④ で 79 点 → ⑤ が `attempt_count += 1` → ② に戻る → ② が要件を再生成
- これは **deficiency の中身に関係なく無条件で AI ループを回す**

問題:
- 「ユーザー定義明確性」の不足は、本来ステークホルダー（ビジネス側）への確認が必要なケースが多い
- AI が ② で勝手に補完すると **事実と異なる仮定** が混入するリスク
- 一方「数値曖昧性」「ファイル間の用語不整合」などは AI 再生成で解決可能

→ **タグで「AI で直せる／人間に確認が必要」を分け、後者が混じる場合は ⑤ で人間ゲートに早期エスカレーション**（attempt_count に達する前に）するのが安全。

## タグ分類ルール

各 deficiency に下表に基づきタグを付与する。

### 軸別デフォルトタグ

| 軸 | デフォルト | 根拠 |
|---|---|---|
| `correctness` | AI改善可能 | 課題と要件のトレースは ② が要件再生成で解消可能 |
| `completeness` | AI改善可能 | UC・データ・非機能の項目漏れは ② が穴埋め可能 |
| `unambiguity` | AI改善可能 | 曖昧語の定量化・閾値追加は ② が定型的に対応可能 |
| `consistency` | AI改善可能 | 用語揺れ・ファイル間矛盾は ② が機械的に解消可能 |
| `user_definition_clarity` | **人間対応必要** | ペルソナ・代替手段・痛点はステークホルダー確認が前提。AI が勝手に補完すると事実と異なる仮定が混入 |

### 軸別デフォルトを上書きするケース

下記に該当する場合はデフォルトを上書きし、明示的に `人間対応必要` を付与：

| 条件 | 軸 | タグ | 理由 |
|---|---|---|---|
| `08-constraints.md` の予算・期間が「ステークホルダー確認待ち」と `02-scope.md` 等で言及されている | correctness / completeness | 人間対応必要 | ビジネス側決定事項 |
| 外部 API 仕様が公開ドキュメントから取得できない（社内 API・有料 API） | completeness / unambiguity | 人間対応必要 | 仕様取得自体が人間タスク |
| 競合分析・差別化要素が要求されているが ① で情報未提供 | correctness | 人間対応必要 | ビジネス判断 |
| 法的・コンプライアンス要件（個人情報・GDPR 等）への適合性 | consistency / completeness | 人間対応必要 | 法務・セキュリティ確認必須 |
| 同一 deficiency が **2 回以上**ループしても解消されていない | 全軸 | 人間対応必要 | AI が解決できないことが実証済 |

逆に、下記に該当する場合は `user_definition_clarity` のデフォルトを **AI改善可能** に上書きしてよい：

| 条件 | 理由 |
|---|---|
| ① の `00-raw-input.md` に必要情報が既に書かれているのに ② がそれを `01-overview.md` に転記し忘れている | 単なる転記ミス、AI で解決可能 |

## タグ付け手順（採点時）

④ AI採点の Step 4（deficiency 記録）に以下を追加：

- **Step 4a**: `deficiency.issue` を確定
- **Step 4b**: 上記「軸別デフォルトタグ」を引く
- **Step 4c**: 「上書きケース」に該当しないか確認、該当すれば差し替え
- **Step 4d**: `deficiency.tag` フィールドに `AI改善可能` または `人間対応必要` を記録
- **Step 4e**: 上書き時は `deficiency.tag_reason` に上書き理由を記録

## `rubric.json` スキーマ拡張案

現行 `docs/interface-contracts.md` の `rubric.json` スキーマに以下フィールドを追加する提案：

```json
{
  "deficiencies": [
    {
      "axis": "user_definition_clarity",
      "doc": "01-overview.md",
      "issue": "ターゲットユーザーが「企業のマーケ担当」とのみ記載で具体業務・代替手段・痛点が未記載",
      "severity": "high",
      "tag": "人間対応必要",
      "tag_reason": "ペルソナ補完はステークホルダー確認が前提"
    }
  ],
  "ai_improvable_count": 0,
  "human_required_count": 0
}
```

`ai_improvable_count` / `human_required_count` は ④ が deficiencies から自動集計。⑤ がこれを参照する。

## ⑤ ループ制御ロジック拡張案

現行（`docs/interface-contracts.md` ⑤）：
```
合格: total >= 80
エスカレーション: attempt_count >= 3
```

拡張案：
```
合格: total >= 80 かつ human_required_count == 0
エスカレーション (早期): human_required_count >= 1
エスカレーション (上限): attempt_count >= 3
ループ: それ以外（AI 改善可能な減点のみ残っている）
```

これにより：
- 人間判断が必要な減点は **1 周目で即** ⑦ 人間ゲートへ → ステークホルダー確認 → 修正再開
- 機械的に直せる減点だけが ② への自動ループに乗る
- 結果として ② への無駄ループが減り、AI コストも削減

## 検証計画（R&D-2 への引き渡し）

R&D-2（ルーブリック採点精度検証）で以下を検証：

| 検証項目 | 合格基準 |
|---|---|
| デフォルトタグの妥当性 | 5人手動採点と AI タグ付けの一致率が **80% 以上** |
| 上書きルールの発動精度 | 上書き発動ケースのうち、人間レビューで「妥当」判定が **90% 以上** |
| AI 改善可能タグの実効性 | AI 改善可能タグの deficiency が次ループで解消される率が **70% 以上** |
| 早期エスカレーション効果 | 人間対応必要タグ早期エスカレーションにより、`attempt_count` 上限到達ケースが減少 |

検証未通過時のアクション：
- 軸別デフォルトの組み換え
- 上書きルールの追加・削除
- 「ハイブリッド軸」の概念導入（軸内でケースバイケース）
