# 要件採点ルーブリック v0.1

> **R&D-1 成果物**
> ④ AI採点 (`ayatori-review-scoring`) で使用する 5軸 × 20点 × 4段階アンカー詳細ルーブリック。
> AYATORI仕様書 §3 ③④ に準拠（ISO 29148:2011 の4品質特性 + 独自軸1つ）。

---

## 採用方針

各軸を 0-20 点で採点し、合計 100 点。合格基準は 80 点（`docs/interface-contracts.md` ⑤ ループ閾値）。

スコアレンジは step-04-scoring.md に既定の 5 段階を維持しつつ、**各軸ごとに「何があれば何点になるか」のアンカー例**を追加。採点者間ばらつきを抑えることが目的。

| Score | Criteria |
|-------|----------|
| 20 | 完全に満たしている |
| 15-19 | ほぼ満たしているが軽微な不足あり |
| 10-14 | 部分的に不足している |
| 5-9 | 重大な不足あり |
| 0-4 | ほとんど満たしていない |

---

## ⚠️ 軸定義の前提（仕様書 vs 実装の不整合）

AYATORI仕様書 §3 ③ は **「ISO 29148:2011 の4品質特性 + 独自軸1つ = 5軸」** を採用：

| # | 仕様書（Confluence ページ 3740237924） | 現リポジトリの実装 |
|---|---|---|
| 1 | 正確性 (correctness) | `correctness` ✅ |
| 2 | 完全性 (completeness) | `completeness` ✅ |
| 3 | 精密性・曖昧性排除 (unambiguity) | `unambiguity` ✅ |
| 4 | 一貫性 (consistency) | `consistency` ✅ |
| 5 | **ユーザー定義明確性 (独自軸)** | **`feasibility` (ISO 29148:2018 の5番目)** ⚠️ |

5番目が **仕様書「独自軸」 vs 実装「ISO の Feasibility」** で異なる。
本ルーブリック v0.1 は **仕様書定義（ユーザー定義明確性）を採用**する。
実装側コード（`pipeline/step-04-scoring.md`、`docs/interface-contracts.md`、`sample-app/rubric.json`）の `feasibility` キー統一は、別 PR でリードB から提案する（本作業のスコープ外）。

## 軸 1. 正確性 (Correctness) — 20点

**評価観点**: 課題と解決策の一致度。要件が「ユーザーの真の問題」を解決しているか。

| Score | Criteria | アンカー例（ai-avatar-video アプリを想定） |
|-------|----------|----------------|
| 0-4 | 要件と課題の関連が読み取れない | 「動画生成機能」が、想定ユーザーが実際に困っている何を解決するのかが書かれていない |
| 5-9 | 課題は記載されているが、要件との接続が弱い・複数の要件が関係ないものを含む | 「効率的に動画を作る」課題に対し、要件に「ユーザー間の SNS 共有機能」が含まれている（課題と関係なし） |
| 10-14 | 主要要件は課題に対応するが、一部に妥当性の薄い要件が混在 | Must 機能 5 件のうち 1〜2 件が、課題ステートメントに登場しない切り口の機能 |
| 15-19 | 全 Must 機能が課題と直接対応しているが、Should/Could に課題逸脱気味のものが残る | Must は完全に課題対応、Should の 1 件が「あれば嬉しい」レベルで課題接続が薄い |
| 20 | 全機能（Must/Should/Could）が課題ステートメントとトレーサブル | 各機能の説明文に「これは課題 X のどの側面を解決するか」が明示 |

**Deep-dive triggers:**
- 課題ステートメントが抽象的（「効率化」「便利化」） → 「具体的にどの作業を／何分から何分に短縮？」を要件側に求める
- Must 機能の動詞が「サポートする」「対応する」 → 課題のどのステップを置換するかが不明、減点

**良い deficiency:**
- 「`05-features.md` F-002（音声試聴）が、`01-overview.md` の課題『動画完成までに5回確認往復』のどの往復を削減するのか不明。試聴が承認フローのどこに位置するかを `03-user-flow.md` に追記が必要」

**NG deficiency:**
- 「課題と要件の対応が弱い」（具体性なし）

## 軸 2. 完全性 (Completeness) — 20点

**評価観点**: 要件の網羅度。実装に必要な情報が抜けなく揃っているか。

| Score | Criteria | アンカー例 |
|-------|----------|----------------|
| 0-4 | 要件項目が大幅に欠落（正常系のみ・受け入れ条件なし・データ定義なし） | `04-use-cases.md` に正常系1パスのみ、エラー・例外なし |
| 5-9 | 主要 UC は記載されているが、エラー/例外/エッジが網羅されていない | 全 UC のうち事前条件・後条件があるのは半分以下 |
| 10-14 | UC の構造は揃っているが、`07-data-definition.md` の外部連携データに項目漏れ | API レスポンス項目の半数が「TBD」 |
| 15-19 | UC・データ定義は揃っているが、非機能要件 (`06-non-functional.md`) のいずれかの項目（性能 / セキュリティ / 可用性）に閾値なし | 「レスポンスは速く」のような定性記述あり |
| 20 | 全UC（正常・異常・エッジ）に actor / 事前 / 主フロー / 後条件あり、データ全項目に型と必須/任意が定義、非機能に数値閾値あり |  |

**Deep-dive triggers:**
- UC タイトルだけで本文がスカスカ → アクター抜けの可能性高い
- 「TBD」「未定」「後で詰める」 → 全箇所カウントして deficiency に列挙
- API・外部連携が出てくるが `07-data-definition.md` で言及なし → 完全性減点

**良い deficiency:**
- 「`04-use-cases.md` UC-003（生成失敗時のリトライ）でアクター（システム / ユーザーのどちらが起動するか）が未記載。`07-data-definition.md` の HeyGen API レスポンスの error_code 項目の値域が定義されていない」

## 軸 3. 精密性・曖昧性排除 (Unambiguity) — 20点

**評価観点**: 数値基準・定量的記述の充実度。曖昧な表現の排除度。

| Score | Criteria | アンカー例 |
|-------|----------|----------------|
| 0-4 | 全体に定量記述が欠落、曖昧語が支配的 | 「快適な操作感」「素早い応答」「使いやすい UI」が並ぶ |
| 5-9 | 一部に数値あるが、判定基準として機能していない | 「3秒以内に応答」だけ書かれ、何の操作で／どの環境で／パーセンタイル？が不明 |
| 10-14 | 主要機能には数値あり、補助機能や非機能の半分は曖昧 | 動画生成時間に SLA があるが、UI レスポンスは「快適」止まり |
| 15-19 | 全機能・非機能に数値があるが、一部で測定方法・パーセンタイルが未定義 | 「平均 3 秒」のみで P95/P99 がない |
| 20 | 全数値に「対象操作 / 環境 / 計測方法 / パーセンタイル」付与、曖昧語ゼロ |  |

**Deep-dive triggers:**
- 「快適」「素早い」「使いやすい」「適切な」 → 全件カウントして deficiency に列挙
- 「〜程度」「概ね」「適宜」 → 同上
- 数値はあるが「何の数値か」不明 → 文脈不足

**良い deficiency:**
- 「`06-non-functional.md` 性能要件で『動画生成は素早く完了する』と記述。`05-features.md` F-001 で長尺動画（5分）と短尺（30秒）の SLA 区別がない。最低限：尺別 P95 秒数と計測対象（API 呼出 → 完了通知 / UI 表示まで）を明記が必要」

---

## 軸 4. 一貫性 (Consistency) — 20点

**評価観点**: ファイル間・記述間の矛盾がないか。

| Score | Criteria | アンカー例 |
|-------|----------|----------------|
| 0-4 | ファイル間に重大な矛盾、同じ用語が複数の意味で使われている | `01-overview.md` で「ユーザー」が個人クリエイター、`05-features.md` では企業マーケが対象になっている |
| 5-9 | 主要矛盾あり（機能数・スコープ・対象ユーザー） | Must 機能数が `01-overview.md` で5件、`05-features.md` で7件 |
| 10-14 | 命名揺れ、データ項目名の不統一 | 「user_id」と「ユーザーID」「uid」が混在 |
| 15-19 | 全体は整合しているが、`02-scope.md` の「対象外」と `05-features.md` の Could に重複・矛盾あり | スコープ外宣言した機能が Could に残っている |
| 20 | 全ファイル間の用語・データ項目・機能 ID・スコープ宣言が完全整合 |  |

**Deep-dive triggers:**
- 全ファイル grep で同一概念の表記揺れチェック（user / ユーザー / クリエイター 等）
- `02-scope.md` の対象外項目を `05-features.md` で検索 → 重複ヒットがあれば矛盾
- 機能 ID（F-XXX）・UC ID（UC-XXX）の参照整合チェック

**良い deficiency:**
- 「`05-features.md` F-004（コラボ機能）が `02-scope.md` で『対象外』に列挙されている。どちらが正なのか優先順位 + 採否を明示が必要」

## 軸 5. ユーザー定義明確性 (User Definition Clarity) — 20点（独自軸）

**評価観点**: ターゲットユーザーの具体性。ペルソナ・利用シーン・代替手段・痛点が定量的に語れるレベルで定義されているか。

| Score | Criteria | アンカー例 |
|-------|----------|----------------|
| 0-4 | 一般属性のみ（性別・年代）でペルソナ無し | 「20〜40代の社会人」 |
| 5-9 | 役割・職種は出てくるが利用シーンが不明 | 「営業マネージャー」 |
| 10-14 | Who / When / Where が具体だが代替手段・痛点が薄い | 「企画職、月曜朝に資料を作る」だけで何に困ってるかが弱い |
| 15-19 | ペルソナ + 利用シーン + 代替手段 + 痛点が揃っているが、定量データなし | 痛点が「面倒」「時間がかかる」止まり、何分・何回が不明 |
| 20 | ペルソナ + 利用シーン + 現在の代替手段 + 痛点 + 定量データ + 「解決したら何が変わるか」 | 「企画職、週1で資料動画を作成、現状は外注で5営業日・10万円。本ツールで内製化、半日・1万円相当で30本/月生成可能に」 |

**Deep-dive triggers:**
- 「忙しい人」「効率を求める人」 → ペルソナ未確定。MoSCoW 優先度判断ができない
- ペルソナ複数列挙（3人以上） → 一次ターゲットの優先順位を求める
- 「営業」「企画」だけで業務文脈なし → 実際の作業フローを聞く

**良い deficiency:**
- 「`01-overview.md` ターゲットユーザーが『企業のマーケ担当』とのみ記載。具体的な業務（広告動画？社内研修？）、現状の代替手段（外注？社内ツール？手作業？）、本ツール導入後の定量変化が未記載。`05-features.md` の Must 機能優先度判断の根拠が不在になる」

## 採点の思考順序（CoT — Chain of Thought）

step-04-scoring.md L17-26 に既定の 4 ステップを継承し、本ルーブリック v0.1 では各 Step に **アンカー参照** を追加：

- **Step 1**: `rubric.json` の各 criteria の description を読み、評価観点をリストアップ
- **Step 2**: `requirements/01-overview.md` 〜 `08-constraints.md` を読み、各観点について **本ルーブリックの 5 段階アンカー** に照らして「どの段階か」を判定
- **Step 3**: アンカーから導かれるスコアレンジを採用、その中で「軽微/重大」を区別して具体スコアを決定
- **Step 4**: 各減点について「どのファイルの・どの箇所が・どのアンカーから何段階下か」を 1 文で `deficiency.issue` に記述

> **採点禁止事項**: スコアを先に決めてから根拠を後付けすること。必ず Step 1〜3 → スコア の順。

## Severity ガイド

`deficiency.severity` は 3 段階。スコアレンジへの影響量で決める：

| severity | 影響 | 例 |
|---|---|---|
| `high` | -5 点以上に直結（軸スコアを 1 段階以上下げる） | 必須要件の欠落、Must 機能のフロー未定義、外部 API 連携の項目漏れ |
| `medium` | -1〜-4 点（軸スコアを同段階内で減点） | 表記揺れ、軽微な曖昧表現、補助機能の数値欠落 |
| `low` | スコアに直接影響しない（次回ループ参照用に記録） | 命名統一の改善余地、補足説明があれば望ましい箇所 |

## ループ再採点時の特則

`attempt_count > 0` の場合、③（`ayatori-evaluation-criteria`）が前回 `deficiencies` を `criteria.description` に反映してくる前提。本採点では：

1. **同一 deficiency が解消されているか** を最優先で確認
2. 解消されていない場合は `severity` を 1 段階上げて再記録（例: medium → high）
3. 新規発見の deficiency も追加するが、`history` フィールドに「前回比 +N 件 / -N 件」を含めると⑤の判断材料になる（オプション）
