# Step 03: Requirements Generation from Raw Analysis

## Purpose

Transform `reverse-engineered/raw-analysis.md` into 8 ISO 29148 structured requirement documents.
Behavioral annotations from the B-01~B-07 checks must be preserved — not collapsed into generic descriptions.

## Process

1. Read `artifacts/{app_name}/reverse-engineered/raw-analysis.md`
2. Generate the 8 documents in dependency order:

| File | Contents | Key behavioral obligation |
|---|---|---|
| `01-overview.md` | Purpose, target users, problem, positioning | PoC scope summary |
| `02-scope.md` | MVP features, out-of-scope, platform | PoC/Product table for ALL UI elements |
| `05-features.md` | 機能カテゴリ別フィーチャーテーブル with I/O and processing（MoSCoW 不使用 — 実装済み機能のカテゴリ別グルーピング） | Must include B-04 upload processing specs |
| `04-use-cases.md` | Actor, pre-condition, basic flow, alt flows, post-condition | Must include B-05 back-nav and B-01 audio behaviors |
| `03-user-flow.md` | Flows with branch logic | Must show B-03 scope branching |
| `06-non-functional.md` | Performance, accessibility, compatibility | |
| `07-data-definition.md` | API endpoints, entities, field definitions | Include B-02 persisted fields |
| `08-constraints.md` | Dev constraints, assumptions, acceptance criteria | |

### `03-user-flow.md` の mermaid ノードラベル規約

`03-user-flow.md` にフロー図 (mermaid) を書くとき、**ノードラベルは「画面名として通用する短い名詞句」にする**
(例: `本人確認・ブラウザ委譲待機`)。画面内の表示文言・操作説明・入力項目の列挙は **ノードラベルに入れず**、
エッジラベル (遷移のきっかけ) または本文 prose に書く。

- 理由: 下流の遷移図変換 (Step 06 の E6 = `scripts/derive-transition-map.mjs`) が、このノードラベルを
  `screens/00-screen-list.md` の画面名と **機械突合** して画面ノード (矩形) かどうかを判定する。ラベルが画面内文言だと
  突合できず、実在する画面が非画面ノードに落ちて下流の L5 connectivity 検査が偽の欠落を出す。
- `※ 推測 (inferred)` / `※ 不明 (unknown)` マーカーの付与は従来どおり — **本規約はマーカーを禁止しない**
  (下流はラベル内のマーカーを逐語保持する)。
- 本規約は LLM 生成 (本 skill) への指示であり **機械強制はしない**。既に生成済みの `03-user-flow.md` には
  遡って効かない **前向き規約** である (既存プロジェクトの突合率は改善しない)。

## Behavioral Annotation Rules

These rules prevent the most common omissions found in reverse-engineered requirements:

**B-01 Audio rule**: If `raw-analysis.md` has B-01 audio findings, `05-features.md` MUST include:
- An explicit feature entry for audio playback exclusion (one audio at a time)
- The auto-stop on navigation behavior
- Not just "play/stop button" — the inter-item exclusion is a separate, distinct requirement

**B-02 Persistence rule**: For every persisted field found in B-02:
- `07-data-definition.md` must list the field with `storage: local` annotation
- `04-use-cases.md` must show the "restore previous value" flow in the UC's pre-condition or basic flow

**B-03 Scope rule**: `02-scope.md` must contain a **PoC/Product element table** that lists every UI element with PoC/Product classification — not just screens. Bell icon, gear icon, new-create buttons: all must be classified. Use the B-03 findings as the source.

**B-04 Upload rule**: For every file upload field, `05-features.md` must include:
- Accepted formats
- Post-upload processing (resize, crop, format conversion)
- Error case when the uploaded file does not meet requirements

**B-05 Navigation rule**: For every screen with a back button in a multi-step flow, `04-use-cases.md` must include:
- Whether state is preserved on back navigation
- Whether a confirmation dialog appears
- What happens to in-progress data if the user cancels

**B-06 Illustration note**: The `illustration_policy` field belongs in `requirements.json`, which is generated by `06-format-convert` (E1), not by this skill. This skill must not overwrite or alter the `### B-06 Illustration Style` section in `raw-analysis.md` (written by Step 02); Step 06 reads that section directly to extract `illustration_policy`.

## Quality Rules

- **DO NOT hallucinate** features not evidenced in `raw-analysis.md`
- Mark inferences with `※ 推測 (inferred)` notation
- Flag missing information with `※ 不明 (unknown)` — do not fill gaps with plausible defaults silently
- **Operating Principle 4 (gap-source-check)**: the three rules above are `docs/principle4-disambiguation.md` §1 Flavor (b) applied to reverse-engineering — every feature/requirement must trace to source evidence (CONFIRMED via Operating Principle 3). An inference without evidence is `(D) UNCERTAIN`: mark `※ 推測`, and if it would change scope (e.g. adding an unevidenced Could-equivalent feature) append to `artifacts/{app_name}/pending-questions.json` with the **full required field set** (schema `required` + hook R3 が無条件要求): `target` / `question` / `raised_by_step="03-requirements-gen"` / `raised_at` (ISO 8601) / **`reflect_to`** (回答の反映先 artifact の `artifacts/{app_name}/` 相対パス。本 skill の出力先なら `reverse-engineered/*.md` — Pre-flight Gate の振り分けに必須で、**書ける値は `skills/_shared/preflight-gate.md` § append 経路 の 7 pattern に限る**。この値は Step 06 の E2-2 が `requirements/*.md` 系へ移行するので、Step 06 通過後に受け手を失うことはない)、任意で `ambiguity_kind` / `options` — ⚠️ **`target` / `question` / `raised_at` を省くと hook R3 (`.claude/hooks/schema-light-check.sh`) が exit 2 で Write を弾く** — rather than asserting it as a real requirement.
- Preserve PoC/product scope flags exactly as detected in the raw analysis
- **文書ベース化 (`roles.docs == "base"` の run)**: 既存文書の骨格 (構成・機能識別子・用語) を尊重して 8 文書へ
  再構成する — 同じ内容をゼロから別語彙で書き起こさない (先方文書との対応が取れなくなり Step 04 の比較も濁る)。
  文書由来の specifics は `doc_backed` + `ground-truth/{file}.md:line`、code 裏取り済み (raw-analysis で backed)
  は `source_backed` に昇格して code ref を採用する
- **Cross-Source Conflicts の消費**: `raw-analysis.md` の `## Cross-Source Conflicts` にある項目は、採用値 (衝突規則の勝者 — code 勝ち) を本文に書き、当該 specific の `reverse-provenance.json` `note` に非採用側の ref を併記する (人間ゲートが両論を追跡できるように)。スコープが変わる未解決衝突は `pending-questions.json` へ append (上記ルールどおり — `reflect_to` に当該記述を持つ文書のパスを併記する)
- Write output documents to `artifacts/{app_name}/reverse-engineered/` (not `requirements/`)
- **MoSCoW 禁止（リバース時）**: `05-features.md` に Must/Should/Could の優先度を付けない。リバース成果物は「実装済み機能の一覧」であり、優先度付けは意味をなさない。代わりに機能カテゴリ（アプリのドメインから導出: 例 「認証・初期設定」「充電スポット管理」「充電記録」等）でグルーピングし、カテゴリ見出し（`###`）でセクション分けする。**この `###` カテゴリ見出しは Step 06 が `00-screen-list.md` の分類に使う正規識別子になるため、全ドキュメントで名称を統一すること。** 推奨フォーマット:

  ```markdown
  ### {機能カテゴリ名}

  | 機能ID | 機能名 | 概要 | I/O | 処理 | 備考 |
  |---|---|---|---|---|---|
  | F-XXX | ... | ... | ... | ... | ... |
  ```

## Provenance Self-Report

This skill is the **single writer** of `artifacts/{app_name}/reverse-engineered/reverse-provenance.json`
(`schemas/reverse-provenance.schema.json`). It is the reverse-path analogue of forward Step 02's
`generation-provenance.json` — it makes the "source-backed vs inferred" distinction **machine-readable per item**,
so the downstream reverse review gate (Step 04↔Step 06) can flag inferred items and a human can focus review there.

**Procedure** (run after generating `01-08.md`, before finishing the step):

1. **Forced-enumerate** every *load-bearing specific* you wrote into `01-08.md` — quantities, formulas,
   thresholds, external API/lib dependencies, data enums/fields, and any claim that asserts a feature
   capability / behavior step / content exists. (Enumeration definition SoT: `docs/principle4-disambiguation.md` §5.2.
   Prose, self-evident structure, and rhetoric are NOT enumerated.) Do not skip — full enumeration is the point;
   it removes the freedom to silently omit an item.
2. For **each** specific, classify its `provenance` (= the **kind of evidence** backing the claim):
   - `source_backed` — you can cite the actual source line in `input-sources/{stack}/`. **`source_ref` is mandatory**
     and must be `input-sources/{stack}/path/to/file.ext:line` (range: `:line-line`). This operationalizes
     CLAUDE.md Operating Principle 3's "cite file:line or mark 未確認". Code-only — never use this label for
     doc/figma evidence.
   - `doc_backed` — the evidence is an archived document (Confluence page, normalized local doc, or
     normalized Jira issue `jira-{KEY}.md`). **`source_ref` is mandatory**: `ground-truth/{file}.md:line`.
     Cite only files whose `ground-truth/index.md` content status is citable (本文 / 本文+図依存 / 薄い系。
     ADF生JSON はノード構造引用) — **殻 / 図のみ / テンプレート未記入 のファイルは引用先にできない**
     (実質本文が無く、監査で誤申告として catch される)。⚠️ Jira 課題由来の記述は「ある時点の変更要求」—
     実装済みであることを code / 仕様書で裏取りできない限り current-state の断定として書かず、
     時点情報である旨を note に併記する。
   - `figma_backed` — the evidence is the archived Figma capture. **`source_ref` is mandatory**. Text evidence
     inside the archive needs `:line`:
     - frame structure / layout / labels / inline styles → `ground-truth/figma/{file_key}/{node}--{slug}.design-context.md:line`
     - **design token values (colors, font sizes) → `ground-truth/figma/{file_key}/variables.json:line`** — cite the
       line of that token key. A token present only in `variables.json` is still evidence-backed; do NOT downgrade it
       to `inferred` just because it is absent from `design-context.md`.
     - purely visual evidence with no text counterpart → the sibling `.png` path (no `:line`).
   - `derived` — deterministically derived from an evidence-backed spec / confirmed value. `derived_from` is mandatory
     (the ref it derives from); add `source_ref` too if a primary line supports it.
   - `inferred` — you could NOT cite any evidence; you wrote it from general knowledge / assumption.
     `source_ref` is null/omitted, and the matching text in `01-08.md` MUST carry `※ 推測 (inferred)`.
   - **Evidence-kind ≠ role**: these labels record what kind of evidence exists; they never change with the roles
     in `source-inventory.json`. In degraded mode (figma = primary), figma-evidenced claims stay `figma_backed` —
     do not promote them to `source_backed`.
   - **Multi-source support**: when both code and doc/figma support the same claim, cite code (`source_backed`);
     a concurring doc/figma ref may be noted in `note`.
   - **縮退モード (code 不在・figma = primary) の厳格化**: 視覚・構造・文言の主張は `figma_backed` で書けるが、
     **挙動・条件分岐・処理の主張は docs に根拠が無い限り必ず `inferred`** — figma を挙動の根拠にしない
     (見た目から挙動を推定して根拠ありに見せるのが縮退モード最大の laundering リスク)。
   - ⚠️ **When unsure, classify as `inferred`** (under-claim → the reverse review gate audit catches it; over-claiming
     an evidence-backed label is the failure mode this guard exists to prevent — recall the ChargeMinder badge case
     where "介入群限定" was inferred but the BE source showed 対象群 could also earn it).
3. Write the ledger via the lazy-init pattern: `Read or {init-stub} → rebuild specifics → Write back`,
   init stub = `{ "app_name": "{app_name}", "specifics": [] }`. ⚠️ `ref` は **ASCII の英数字 / `_` / `-` / `.` / `[]` だけ**で構成する先頭英字の dot/bracket 文法
   (`^[A-Za-z_]...`) — 文書番号 (`01-overview.…` / `08-…`) を ref の先頭に使うと hook が Write ごと弾き、
   台帳全体の書き直しになる。文書由来の specific は `OV-01.…` / `CO-01.…` のような英字プレフィックスを使う。 On loop re-run,
   overwrite the whole file (symmetric with regenerating all of `01-08.md`). Assert `app_name` is present/non-empty
   before Write. The `.claude/hooks/schema-light-check.sh` R8 rule enforces required fields + the
   `source_backed → source_ref(file:line)` invariant at write time.

⚠️ This ledger is a **self-report**, not the final verdict. The reverse review gate (Step 05) runs
`ayatori-requirements-auditor` (layer=reverse) which re-judges provenance against the actual evidence
(`input-sources/` code, `ground-truth/` doc archive, `ground-truth/figma/` capture archive) and does
**not** trust these labels (an evidence-backed label you cannot actually trace will be flagged). Honest `inferred`
labels here make that audit cheaper and the human review sharper.
