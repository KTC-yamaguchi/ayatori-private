# Artifact File Responsibility — `artifacts/{app_name}/` 配下のファイル責務

> 本ファイルが責務マップ・設計原則の正本 (SoT)。`CLAUDE.md`「Artifact File Responsibility」節には要約と gotcha のみを残し、詳細は本ファイルに一本化する。Operating Principles 本文とプレースホルダ `{stack}` / `{platform}` の定義は `CLAUDE.md` を参照。

`artifacts/{app_name}/` 配下のファイル責務を明確に分離する。**「純粋な記述 (description / INPUT)」** と **「パイプライン状態 (state / OUTPUT)」** を別ファイルに保持する原則。各 step skill は SoT (Single Source of Truth) のファイルだけを書き、他 step の責務領域には触らない。

## 設計原則

1. **記述 / 状態の分離**: 「要件は何か」(`requirements.json`) と「いま step がどこまで進んだか」(`pipeline-state.json`) を絶対に混ぜない。
2. **ループ不変量 / 履歴の分離**: criteria 定義 (`rubric.json` / `wcag-mapping.json`) と attempt ごとの結果 (`scoring-history.json` / `wcag-history.json`) を分ける。`attempt_count` 等のメタ field は履歴ファイルの `len(attempts)` から導出する (専用 field を持たない)。
3. **単一所有権**: 1 ファイルにつき 1 つの主たる writer を決める。複数 step が同じ key に書き込まない (例: WCAG attempt の append は 11-wcag-mapping のみ)。
4. **lazy 初期化**:
   - **Writer contract**: 最初の writer は各 artifact 所定の init stub (pipeline-state.json は `{ "app_name": "{app_name}" }`) から init する。以降は `Read or {init-stub} → merge → Write back` パターン。skill のドキュメント内表記 `Read or {}` は **shorthand であり、実際の `{}` リテラルではない** — file が存在しない / Read object に `app_name` が無い場合は必ず init stub に置換してから merge を行う。
   - **必須 field の保全**: schema `required: ["app_name"]` を満たすため、writer は **Write back 直前に `app_name` field が存在し非空であることを assert** する。欠落していたら現在のディレクトリ名 `{app_name}` を補完する。
   - **廃止 field `schema_version` の許容**: かつて多くの artifact に書いていた informational マーカー。値を読んで挙動を変える実装が repo に一度も存在しなかったため書き込みを廃止した。既存 artifact に残存する値 (旧版 writer が書いた値を含む) は受理して無視し、`Read → merge → Write back` での carry-over も無害 (能動削除もしない)。各 schema には deprecated property として宣言を残す (`additionalProperties: false` の下で既存 file を valid に保つため)。
5. **feature flag 分離**: `FIGMA_MCP_ENABLED=false` のとき不要なファイル (`figma-state.json`) は `pipeline-state.json` に混ぜず、別ファイルにする。
6. **schema strict は新規プロジェクトのみ**: 既存 artifacts (TournamentBracket / DecisionPath 等) は legacy として保持。新規プロジェクトのみ本責務分離が適用される。
7. **state SoT の最小化**:
   - **runtime state** (resume / skip / phase 完了判定) の SoT は **`pipeline-state.json` のみ**。
   - `requirements.json` は **INPUT artifact**。例外として `requirements.json.status == "REVERSE_ENGINEERED"` は Phase 0b が **一度だけ書く origin sentinel** であり runtime state ではない (Phase 1~5 から書き換えない)。Preamble がファストパス mode を選ぶための分岐記号として読むだけ。
   - `session-handoff.md` は **disposable summary** であり state 判定に **使用してはならない**。
   - **長期方向**: REVERSE_ENGINEERED の判定も将来的には `pipeline-state.json.origin` のような専用 field に移し、`requirements.json` を完全に INPUT-only にする。現状の `requirements.json.status` 参照は実用上の暫定措置。

## file_topology の参照先

- `pipeline.yaml` の `file_topology` セクション = mode_agnostic (常に生成) / conditional (env / status で生成) の網羅的インベントリ。
- phase.input / phase.output で宣言されているファイルは file_topology に再掲しない (SoT 原則)。
